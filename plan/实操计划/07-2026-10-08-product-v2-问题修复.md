## 酒店 touch bar 的设计

1. 比较前明确预算口径、独立房间/宿舍接受度、禁烟/床型、可接受价位。用户说“全程6万、酒店每晚2–3万”时，两种预算并存，不把6万替换成酒店预算。只在性别限定房型确实相关时确认资格；未确认不当通用推荐。
2. 查询现有乐天空室 API；选择最多8家不同酒店，有5–8家时横向展现，没有足够来源时如实显示实际数量。数量增加不放宽每run/每日调用和金额边界，长行程仍遵守逐晚核价限制。
3. 排序优先满足硬性资格与房型，再看目标价位、评分与评价数（仅来源提供时）、住宿位置与已规划景点。当前适配器尚未保留酒店地址/坐标/评价数，须先验证乐天响应并保留这些来源字段；缺失时显示未知，必要时在预算内复用既有Google定位。不能用城市中心坐标代替酒店坐标。距离/评分缺失不造值；标出推荐依据与未核验项。上限预算不是最低消费，不能只为花满预算排除好选项。
4. 卡片使用等宽内容区、固定底部行动区，支持触屏滑动、触控板、鼠标按钮、键盘焦点；纵向页面滚动不能被劫持。每张卡显示独立酒店、可切换房型、统一入住条件、含税总额/未知原因、时效与来源。
5. 条带末尾“在乐天查看全部酒店”打开酒店搜索结果页，使用可核实的城市/日期/人数/房间条件。价格/禁烟等筛选参数只有验证支持才带入；不能借猜测参数给用户错误筛选结果。供应商空/失败时这个入口仍可用并说明状况。
6. 用户发送乐天酒店页面：支持已核实的官方酒店介绍/套餐URL，安全解析hotelNo，去掉追踪/敏感参数；通过现有hotel_id重查本次日期人数报价，位置仅在取得来源字段或既有Google核实后使用，再呈现“你选的酒店”。登录/预订输入页不抓取；无法识别酒店时提示复制介绍页，不能把地址解析失败写成保存成功。不任意抓取URL，不允许重定向到外部地址。
7. 确认后保存到本次行程的新版本。只有URL、无空房或没有可验证报价时，将规范化酒店标识/介绍地址保留为本旅行的“用户选择的住宿参考，价格/可订状态待核验”，不因查价失败丢掉选择；它与报价Evidence分开，不计作已验证住宿总价或已订房。正式版本仍受partial/conflict规则控制：硬冲突不确认，允许的partial在明确提示后保存；无法确认时参考与未完成草稿仍可恢复。相关持久字段/内部契约先写清兼容设计，不能绕过校验器。
8. 新旅行、换日期、无空房、限性别资格未知、宿舍床位非独立房间、儿童价未知、跨多晚同房型不可得、外链无效、重复选择、断网和报价过期都要有明确处理。

## 最低边界回归矩阵

| 边界 | 必须维持的不变量 |
| --- | --- |
| 初次打开/新标签/新旅行/切历史 | 默认可以明确恢复上次旅行；新标签本身不默建新旅行；“新建旅行”后显示空摘要，不加载旧旅行结果作为本次结果 |
| 同一身份建第二旅行 | 复用 user/token，创建新 session，不重新 demo/login 导致旧历史变成另一身份 |
| 两标签并发/切换时旧SSE迟到 | 路由/状态绑定session+run；版本冲突提示，不最后写入者静默覆盖；旧事件不得覆盖当前选择 |
| 发送响应丢失/重连/SSE重复 | 保持 client_message_id、sequence 去重；读历史不自动重跑、不重复付费 |
| 数据库/网络失败/服务重启 | 保留已提交正式版本；读失败显示错误，不显示“没有行程”；响应未知先查状态再重试 |
| 草稿过期/条件改变/已有正式版本 | 保存再校验 revision/base_version/时效；冲突给下一步；修改旧行程用patch，新旅行新session |
| confirm双击/提交成功但读回失败 | 幂等只生成一个版本；将确认成功和读回失败分开，恢复读回不再保存第二份 |
| no-op/浮点与文本/隐藏默认值 | Decimal金额与规范化语义比较；无变化不增revision，不注入“京都/50000”等事实 |
| 日期/预算/人数边界 | 结束早于开始拒绝；当天往返不搜住宿；0儿童不同0岁；人数房数不能平均分配时总价未知；跨币种不假换汇 |
| 限制房型/无价格/多晚缺报价 | 限制资格不明不推荐为适配；未知不填0；未拿同酒店同套餐同房型所有晚报价不声称总价完整 |
| 候选不足/重复/结果过长/额度不足 | 实际不同酒店计数，截断可见；已有候选保留；不循环查到凑够8家、不扩大额度 |
| 用户URL/富文本内容 | 官方允许域/路径校验；拒绝非HTTPS、伪域、脚本、内网、含认证数据链接；不执行HTML/页面指令、不抓任意URL |
| warning去重 | 同类别可汇总，但不同路段冲突不丢；位置可追踪 |
| 部署前后端不同步 | API新增字段向后兼容；旧前端/新后端及反向兼容要验证；上线失败定位到单commit/部署 |

## 如何隔离错误与回退

- 实施前创建独立Git worktree（按仓库工作树技能流程），在新分支开发；先确认原checkout干净并切回旧分支，再让新worktree使用新分支，不能强制同一分支同时检出。用户原checkout的工作文件不用于试验。若用户后来有未提交修改，先核对，不能stash/reset覆盖。当前分支准备只切换分支，代码内容未变。
- 单元测试先复现真实失效行为，再修实现；事务、并发、持久恢复使用专用临时 PostgreSQL 数据库，不能用mock证明落库成功。线上保留的旧旅行不做测试夹具。
- 一个提交只处理一个可独立验证的行为，并附Bug ID、验证、风险与文档链接；不得凭“运行未抛异常”宣称成功。前一阶段不满足退出条件，不能开始依赖它的下一阶段。
- 每项：失败用例 → 实现 → 相关回归/静态检查 → 自审/独立审查 → 修正 → commit → push。本阶段检查通过后仅在代码变化或新失败时扩大/重跑测试。
- Railway当前auto deploy开启，Wait for CI未开启；分支隔离本身不隔离production。默认先在隔离本地环境完成该增量的相关Chrome验收、检查/测试/独立审查，再推送业务commit；如果验收必须依赖线上环境，先确定预览或暂停自动部署后按验收完成的commit发布，不能把未验收代码直接推给production。推荐补三服务Wait for CI并验证实际生效，但它不能挡住“CI通过、体验仍未验收”的问题。本轮仅切分支，不改变其他开关。
- 线上异常先定位部署与commit，使用 Railway前一成功部署回退恢复服务，之后 git revert 有问题的提交并修复，保留事故证据。代码回滚不等于数据回滚：迁移采用可兼容的增量字段，迁移前备份且验证恢复；不自动drop/reset生产数据。
- 旧分支和基线SHA可追溯；不保证零错误，承诺发现后定位、修正、验证并记录。付费实测仅在授权预算内，默认离线，不恢复旧大批评测。

每个问题的过程记录采用同一模板：输入/前提 → 实际/期望 → 浏览器/run/代码版本证据 → 假设与排除 → 根因如何验证 → 选定方案及其他方案取舍 → 关键实现文件 → 首次失败测试及修复后结果 → 邻近边界回归 → commit/部署/回退 → 仍未知的限制。记录失败尝试，不只留下成功结果；截图和日志脱敏，不上传token、密钥或无关浏览器账号。

优先形成五个面试案例，实际完成前都标为“候选”：

1. **会话隔离与一致性**：多个标签/请求/流式事件如何与当前旅行绑定；为何数据库是业务真相，localStorage不是完整历史。
2. **Agent成功与业务提交分离**：模型说“完成”为什么还不能保存；草稿、确定性校验、用户确认、幂等事务、读回如何闭环。
3. **酒店推荐与可信报价**：套餐去重不等于酒店去重；未知价、限制房型、目标预算、供应商失败和用户外链如何处理。
4. **版本与失效边界**：隐藏默认值造成的候选变化、no-op更新、报价有效性与正式行程持久性怎样分开。
5. **可回退发布与排错**：一个功能一个commit、兼容迁移、CI/Chrome验收、部署失败与恢复证据。不能把AI协作全写成个人手工完成，不能编造准确率提升。
