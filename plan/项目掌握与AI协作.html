项目掌握与 AI 协作

代码可以由 AI 协助生成。
关键决策、问题定位、取舍和验证，要经过你的脑子。

适用：旅游 Agent · M0–M4用途：学习流程，非完成记录离线可读，无外部脚本
01 先判断→02 看增量→03 亲自验证→04 独立复述
01

掌握标准

看你能独立完成什么，而不是记住多少术语。

一个准备写进简历的能力，应能独立完成四件事：

  • 画出来请求从入口到结果经过哪些模块，状态在哪保存。
  • 解释选择为何这样分层，考虑过什么替代方案，代价是什么。
  • 定位失败根据输入、Trace、数据库/工具状态找到失败位置。
  • 验证与改动预测一个小变更会影响哪里，完成改动并运行相关回归。

不必逐字手写或背类名；能独立解释和验证，才算掌握。

不设“必须手写多少代码”的比例。没有真实故障时可以主动注入，但要标明实验；AI 生成日志不等于你已理解。

沿真实输入追到状态与结果，不必先读完整个仓库。

下列路径均相对各自上游根目录，固定版本见来源记录。先读 Messages API 的游客路径，其他运行时按比较需要再读。

Commerce 一次请求的路线：

  → examples/demo_common/storefront.py：请求路由
  → examples/demo_common/host.py：stream_turn
  → shopping-agent/runtime-messages-api/shopping_agent_runtime/orchestrator.py

      → 模型续接 / 结束

这是上游链路；自己的任务 worker、事务提交与事件重放是新增设计，不能画成上游已有。

DataMind 只先读业务相关链：

04

每次开发怎么做

每完成一个功能，经历一次判断、验证和复述。

开始前：你先形成判断

让 AI 调查相关代码并给出简短设计。随后你用自己的话回答：

  1. 这个模块解决什么可观察的问题？
  2. 输入、输出和必须成立的条件是什么？
  3. 它读写哪些状态，和哪几个模块交互？
  4. 备选方案是什么，为什么当前选这个？
  5. 哪个最小实验能证明这个选择有效？

答不清时，先让 AI 解释该处或写最小探针，不急着生成大模块。重要取舍由你确认，普通实现细节交给 AI。

实现中：一次一个可验证增量

以计划保存为例：PlanPatch schema → validator → 数据库事务 → 确认 API → Agent 接入 → UI → 故障测试。每一步有可运行结果，不按任意代码行数拆分，也不一次实现整个框架。

每个增量读三个位置：入口、关键状态读写、失败处理。查看 diff，自己先预测正常/异常输出，再运行验证。若实际与预测不符，先查 Trace 或断点，不直接让 AI 全量重写。

模块完成后：先复述，再整理

你脱离 AI 说明：问题、旧行为、选择、关键调用链、一个失败情形、验证结果。然后让 AI 基于你的回答和真实 diff 补充遗漏，并整理日志。

代码完成与掌握程度分别记录：

  • 实现：TODO / implementing / verified。
  • 理解：能独立解释 / 需复习某点。
  • 证据：commit、case_id、命令、结果或 trace。

不要求每个小改动都停下来写文章；在一个完整功能边界做一次复述和日志即可。

05

阶段与专项练习

开发按计划推进，学习靠这些亲自完成的动作。

阶段你必须亲自做留下什么
M0画一条官方调用链；逐项实测 DeepSeek 兼容差异；在 CLI 跑通一次工具往返，并在 Langfuse 里读懂这条 trace复用清单、协议实测记录、第一条 ADR（为什么手写循环、为什么存中立消息格式）
M1用自己的旅行条件跑完整流程；先预测局部修改影响的字段，再看 diff/Trace一条从用户输入到保存的工程日志
M2让假供应商“订单已创建但响应丢失”，先预测系统状态，再看对账结果；执行中杀进程，确认重启后不重复写入；从一个真实失败的 trace 找到第一个出错的位置预订状态机图、故障步骤与状态前后值、一条归因 → 修复 → 回归记录
M3先预测“固定流程”和“模型自主选工具”谁更好，再跑对照；比较三家模型；用 Claude Desktop 连一次自己的 MCP server对照报告、模型对比表、保留或关闭某项优化的 ADR
M4从干净环境一键启动；冻结 test 跑 3 次并解释波动；完成一个隐藏故障的定位和一个小改动的回归评测报告、三套演示、C 档 ADR

三项重点练习：

  • 编排对照：先预测哪些任务需要模型自主选工具、哪些用固定流程就够，再跑对照；能解释为什么自主编排可能更慢、更贵，以及最终怎么取舍。
  • Trace 归因：让 AI 隐去注入故障的答案；你先列假设与证据，找第一个出错的位置。修复后跑原 case 和一个相邻的正常例。
  • 预订故障：分别注入超时、429、响应丢失，先画出你预期的状态变化，再对照实际结果；能讲清“为什么状态不明时不能直接重试”。

不要求实验都有正向收益，要求能解释结果。受限规划子 Agent 属于 C 档，只写 ADR，是否实现由编排对照的结果决定。详细指标以评测验收为准。

06

日志与决策

只保留一份工程日志；重要取舍再写短 ADR。

开发开始后维护 docs/ENGINEERING_JOURNAL.md；只有重要选择才新建 docs/decisions/NNN-topic.md。按实际完成的功能记录。

工程日志每个功能一条：

展开可复制模板
## Feature / 日期 / 实现提交

1. 问题：用户或系统遇到什么现象？
2. 原行为：沿哪个入口、状态或调用链确认？
3. 方案：输入输出、主要改动和不变量。
4. 取舍：至少一个备选；为何选择当前方案；付出什么代价？
5. 问题与定位：真实故障 / 主动故障注入 / 本次未遇到，明确标注。
6. 解决：修改哪个机制，为什么能解决？
7. 验证与结果：命令、case_id、输出、限制；不要只写“测试通过”。
我的复述：用自己的话概括；仍不理解的点是什么？

ADR 每条尽量短：

展开可复制模板
# ADR-NNN 标题
状态：proposed / accepted / superseded
背景：具体约束与已有行为。
决策：选择什么，适用范围是什么。
备选：比较 1–2 个实际可行方案。
代价：复杂度、延迟、成本或可扩展性的取舍。
验证：实验/回归链接；什么结果出现时需要重新决策。

适合本项目的 ADR：模型协议与复用边界；旅行状态为何独立于聊天摘要；数据库条件提交；SSE 与 worker；证据过期；压缩策略；是否使用规划委派。

07

复制协作提示

按当前阶段选一条即可，不需要每轮全套执行。

模块设计前：

当前只做任务【ID/模块】。先读取相关源码，给出旧调用链、输入输出、状态读写、一个推荐方案和一个可行备选，以及最小验证方法。区分上游事实与新设计。先不要实现，先让我回答为什么选择这个方案。

开始一个增量：

按已确定的方案完成【本次增量】，只改必要文件，保留已有行为。报告关键 diff、测试命令和实际结果、未验证部分。不要顺手扩展其他模块，也不要虚构运行结果。完成后给我四个理解问题，暂不提供答案。

模块结束：

先听我复述这个功能，检查我对调用链、状态、失败和取舍的理解。请用源码和运行证据纠正错误，不因为术语正确就判定掌握。我回答后再整理工程日志；无法确认的地方保留待验证。

练习定位：

从我已学过的模块选一个可逆故障场景，在隔离测试环境准备复现。先给现象和必要日志，不提前告诉根因。让我提出假设、查证和修复，再核对是否定位正确。将故障注入标为实验。
08

独立自测

重点回答 Why、Failure 与 Trade-off。

先讲用户问题，再讲实际链路，最后讲取舍和验证；避免开头罗列一串技术名。

以下问题先自己回答，不提前背 AI 口播：

  1. 为什么一个主 Agent + Skills 足够？什么证据会让你增加子 Agent？
  2. 为什么旅行条件不能只放在消息历史或摘要里？
  3. 日期改了，哪些证据要失效，哪些可以继续用？
  4. 为什么模型只给 ID，价格由服务端填？
  5. 哪些规则必须由代码判断，而不是写进 prompt？修复循环为什么要设上限？
  6. 为什么模型不能直接下单？对话里说“用户已确认”为什么无效？
  7. 下单超时、不知道成没成功时，为什么不能直接重试？对账怎么做？
  8. 数据已提交但响应丢失，重启后怎样识别之前的成功？
  9. SSE 重连为什么不应该重新调用模型？
  10. 为什么存中立消息格式？DeepSeek 兼容接口和 Claude 原生接口哪里不同，你是怎么发现的？
  11. 压缩上下文时如何保证工具调用配对合法？
  12. 任务失败时，如何从 trace 区分理解错误、工具选错、供应商故障、过期事实和状态写入错误？
  13. 怎么防止“少回答或一律拒绝”拿到很高的评测分数？LLM 评审怎么校准？
  14. 固定流程和自主编排的对照说明了什么？哪个优化最终被关闭？
  15. 为什么只读工具做成 MCP，预订不做？
  16. 为什么手写循环而不用 LangGraph？用了会省掉什么、失去什么？

每个准备重点讲的功能，至少展示：一个真实输入、一段核心代码或图、一个实际验证结果，以及一个具体取舍。失败案例可来自实际调试或明确标注的故障注入。

最终做三次独立练习：5 分钟画图讲完整流程；根据未知失败 trace 定位；增加一个小字段或约束并说明回归范围。未通过的部分回到对应单元补练。

理解不足时回到对应模块补练，不靠追加组件解决。
