**旅行规划 Agent（个人项目）**

个人项目。用户从攻略文章出发，通过对话比较酒店、生成并修改京都 2–3 天行程，确认后模拟预订。模型负责理解需求和编排工具，后端负责事实校验、约束检查和失败恢复。独立设计并实现；代码由 AI 辅助生成，我负责架构决策、评测设计与调试。

**技术栈：** Python / FastAPI / PostgreSQL / Next.js；tool calling（Anthropic Messages 格式，DeepSeek、Claude 可切换）/ MCP / OpenTelemetry + Langfuse

1. **结构化状态管理：** 把日期、人数、预算存成带版本号的结构化状态，不依赖聊天记录；条件变更时，相关报价和路线自动失效重查。在 [N] 条多轮用例中，不沿用旧条件的通过率为 [X%]。
2. **工具设计与防幻觉：** 设计 [N] 个工具，模型只返回 ID，价格、营业时间等由服务端按 ID 填入，并标注来源和获取时间；工具结果区分「查无结果 / 接口失败 / 信息未知」，事实准确率 [X%]。
3. **生成—校验—修复循环：** 模型排行程，代码校验时间冲突、营业时间（OpenStreetMap 数据）和预算，不通过时把具体冲突反馈给模型修正，最多 [N] 轮；用户「只改第二天下午」时以 patch 局部修改，其余安排保持不变。
4. **预订的安全与幂等：** 模型只能锁房，下单必须由用户在页面确认；下单请求带幂等键，供应商超时或状态不明时先对账再处理。故障注入测试覆盖重复点击、服务重启、响应丢失等 [N] 种场景，均无重复下单。
5. **评测与模型对比：** 建立 [60] 条评测集（含失败路径与注入攻击），规则断言 + LLM 评审打分，角色语气一致性单独评测并经人工校准；对比 DeepSeek、Claude、GPT 的任务完成率、工具调用准确率与单次成本（[X] / [Y] / [Z]）。另比较了「代码固定流程」与「模型自主选工具」两种编排：[结论]。
6. **可观测与问题定位：** 用 OpenTelemetry 记录每次模型调用和工具调用，在 Langfuse 中查看；对 [N] 个真实失败用例完成从 trace 定位根因到修复回归的全过程。

**30 秒介绍：** 用户读完攻略，还要比较酒店、查路线、反复改行程。我做了一个让模型调用工具出方案、由代码校验事实和约束的 Agent。重点做了三件事：回答都能追溯到来源；改行程只改相关的那一天；预订在崩溃和重复点击下不会重复下单。我还用评测集比较了几个模型的效果和成本，以及 Agent 自主编排到底比固定流程好在哪里。

## 写法约定

- 一条只讲一件事，主语是「我做了什么」。
- 每条至少有一个具体对象（工具数、用例数、组件名）和一个结果位。
- 只用行业通用词：tool calling、幂等、对账、trace、评测集。不用自造术语。
- 每句都要能接住「具体怎么做的？给我看代码」。
- 实验结论是「没有收益、已关闭」时，照实写，这本身就是取舍能力。
