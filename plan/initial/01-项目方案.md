# 01 项目方案

状态：拟实现。事实依据见 [来源清单](06-来源与待验证事项.md)。本文的业务目标、产品流程与技术选型均为本项目设计，效果尚未测量。

## 1. 一句话定位

做一个**从旅游内容阅读到旅行决策的 Agent 应用**。它结合内容库、地点事实和酒店供给，帮助用户把“这篇攻略挺感兴趣”转成“符合我的条件、能解释依据、可保存和继续修改的旅行方案”；同时给内容运营人员提供检索诊断和修改草稿能力。

这个场景足够具体，又能覆盖 Agent 的关键工程问题：动态选择工具、多步任务、跨轮状态、外部数据可信度、来源冲突、权限与副作用、任务恢复和评测。

## 3. 可使用的业务背景

可公开、诚实地陈述：

> 面向旅游内容网站的读者，传统文章呈现的是某种通用旅行建议；用户需要结合日期、同行人、预算与交通方式继续决策。本项目探索用 Agent 连接内容检索、事实核验、酒店比较与行程编辑，并用运营 Agent 帮助内容团队发现检索覆盖和资料缺口。

这是一条**待验证的产品假设**。DataMind 的媒体功能方案也讨论了阅读后的推荐、个性化和后续访问，但里面的流量、跳出率和收益预测仅属于仓库作者的文档表述，本项目没有独立业务数据，不复制为已验证现状或个人成绩。[D07](06-来源与待验证事项.md#d07)

项目完成后可以说“基于真实公开业务场景设计并完成原型”；只有存在部署、用户日志和合作证据，才可以说“在某公司实际落地”或“带来转化提升”。

## 4. 用户、场景与任务

| 用户 | 进入应用时的需求 | Agent 的任务 | 成功的可观察结果 |
| --- | --- | --- | --- |
| 内容读者 | 看了一篇京都亲子攻略，想知道适不适合自己 | 提取文章上下文，澄清必要条件，推荐相关内容与地点 | 推荐依据可追溯，地区/年龄限制不被编造 |
| 准备出行者 | 两晚旅行，有酒店预算和活动偏好 | 检索酒店报价、核对条件、比较候选、生成行程 | 比较口径一致，缺失费用明确，行程冲突可见 |
| 已有方案者 | 下雨、同行人变化或想少走路 | 更新当前旅行状态，局部重规划 | 硬条件保留，修改差异可见，旧结果不会覆盖新请求 |
| 返回用户 | 想继续上次保存的计划 | 恢复计划与当前任务，重新获取需要更新的事实 | 区分历史方案与当前报价，不把旧价格当作现价 |
| 内容运营 | 亲子查询总找不到合适文章，想补齐标签或摘要 | 检索诊断、聚合自有日志、生成修改草稿 | 有原文依据、前后差异、版本检查与确认记录 |

第一版只覆盖一个城市的短途旅行，中文交互、日文/英文资料可按授权接入。跨语言地点别名和译文必须保留原始名称及来源；不能通过译文猜测地点 ID。

## 5. 产品形态与完整交互

独立 Next.js 应用包括四个页面：内容示例页、游客工作台、已保存行程页、运营工作台。读者可以从自己示例文章的“按我的情况规划”按钮进入，也可以从首页直接输入需求。无法嵌入别人的页面不会阻止完整演示。

游客工作台左侧是对话，右侧是文章/地点/酒店卡片、比较表和行程时间轴。进度只显示“检索内容”“核对酒店条件”“检查行程”等业务状态；工具协议、模型 token 和完整 trace 放在开发调试页。

建议演示流程：

1. 用户从亲子示例文章进入，输入“下个月去两晚，两个大人一个孩子，不租车”。
2. Agent 读取文章背景与当前请求，询问具体入住日期、儿童年龄以及酒店预算；已有信息不重复问。
3. Agent 检索自有内容、候选地点，选择需要补充核验的事实；不能核验的项目显示“待确认”。
4. 获得日期/人数后查询酒店，按相同入住条件比较含税总价、退款条件和区域适配。测试模式的报价整块显示“演示数据”。
5. Agent 生成两天方案，代码检查时间冲突、预算口径、路线与已知开放时间。结果提供来源、检查状态及用户可编辑项。
6. 用户改成“第二天少走路”，只修改有关安排；显示变更摘要，保存为新版本。
7. 有合法有效的供应商跳转地址时，用户打开 OTA 页面完成后续操作；无凭证时该操作不可冒充真实订购。
8. 用户关闭页面后返回，恢复保存的行程；报价与需时效核验的信息重新获取。

内容运营演示：输入“哪些京都亲子需求没有被我们的文章覆盖”；Agent 查自有内容与模拟检索日志，列出证据和候选改动；点击草稿显示修改前后；运营本人通过受权限控制的按钮确认，后台再次检查版本后应用。它不能更改 Booking/Agoda 的房价或库存。

## 6. 技术选型与作用

以下均为本项目选择，具体版本在 P0 锁定。

| 技术 | 作用 | 采用范围 |
| --- | --- | --- |
| Python、asyncio | Agent loop、工具并发、适配层、取消与预算控制 | 内核 |
| FastAPI、Pydantic | API、领域校验、工具参数/结果、事件契约 | 后端 |
| DeepSeek | 决策、条件提取、解释、受限规划/记忆提取 | POC 模型 |
| Commerce 的小范围固定版本复用 | 参考共同机制、Messages runtime 和展示扩展 | 先验证再选择具体复用模块 |
| Next.js、React、TypeScript | 独立工作台、结构化卡片、行程与变更预览 | 前端 |
| PostgreSQL | 内容、身份、行程版本、会话、草稿、任务检查点与事件 | 持久化 |
| 全文/关键词检索；可选向量召回 | 自有或获授权文章检索 | 先基线，向量方案由评测决定 |
| MCP 客户端与自有内容服务 | 标准化工具连接；与内部直接调用作对照 | P3 |
| pytest、契约测试、前端关键流程测试 | 验证领域不变量、故障和交互 | 按风险选择测试 |
| 结构化 trace；可选 OpenTelemetry | 记录工具选择、用量、来源与失败 | 不记录敏感全文/密钥 |

不要求同时上 LangChain、LangGraph、Redis、Kafka。只有明确问题和测量结果支持时增加框架或基础设施。Agent 技术深度通过可执行机制与实验体现。

## 7. 核心工作及展示重点

| 能力 | 真正要实现的工作 | 可展示证据 |
| --- | --- | --- |
| Agent 工具循环 | 模型提出行动，执行器校验，结果回传，预算内迭代 | 多步轨迹与协议测试 |
| 约束与来源 | 关键事实由已验证 ID 补全；硬约束由代码检查 | 伪造价格/ID 被拒绝的用例 |
| 检索与状态 | 当前意图优先、检索放宽记录、上下文压缩不丢硬条件 | 检索与多轮回归结果 |
| 规划与委派 | 受限规划子任务、结构化结果、父级重新验证 | 与单 Agent 的消融比较 |
| 运营写入 | 暂存变更、预览、授权确认、版本与幂等控制 | 未确认不能写入的轨迹 |
| 恢复能力 | 取消、断流恢复、任务检查点、重复请求处理 | 故障注入演示 |
| 工程评测 | 基线、评分、成本、延迟、失败分类 | 可重跑报告与样本 trace |

最终希望证明的是“我能设计、实现并评测受业务约束的 Agent 系统”。业务提升、稳定性、效率等具体数值都要等实验或真实使用后再写。
