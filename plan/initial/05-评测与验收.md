# 05 评测与验收

状态：评测方案与建议门槛。本文全部数量/阈值都是**拟定验收标准，不是已经测出的结果**。真实指标在实现后用版本化数据生成。

## 1. 要证明什么

1. Agent 能在多轮请求中完成真实形态的任务，而非只生成一段通用攻略。
2. 关键事实可追溯、硬条件由系统检查、权限不能被模型文字绕过。
3. 状态、记忆、委派、MCP、恢复各自解决了可解释的问题。
4. 能识别并说明未知、冲突、失败和部分完成，不把它们伪装成成功。
5. 所增加的复杂度有质量、恢复能力或使用体验收益，且成本/延迟可接受。

DataMind 的评测包含代码 graders、模型 graders 和基线对照。这里借鉴其评测形式，重新定义领域与来源可见性，不照搬其中面向特定角色的文风约束，也不使用必须隐藏来源的规则。[D06](06-来源与待验证事项.md#d06) [D10](06-来源与待验证事项.md#d10)

## 2. 三层验证

| 层 | 主要证据 | 目的 |
| --- | --- | --- |
| 协议/领域测试 | 假 client、fixture、adapter 契约、数据库事务测试 | 校验与恢复是否真的执行 |
| 离线任务评测 | 自制/获授权测试集、模型真实运行、trace 和评分 | 完成能力、事实与成本比较 |
| 受控在线核验 | 凭证/权利允许的实际接口 smoke 记录 | 当次接口与字段是否可用 |

供应商沙箱或 live smoke 不能替代离线算法对比。离线数据不使用未经允许的第三方接口响应；Google Maps 内容不进入训练/模型验证基准。[W15](06-来源与待验证事项.md#w15)

## 3. 建议数据集

初始目标 120 个任务样例，每个任务可以包含多轮与故障条件；不是 120 条随意改写的单句。建议 20 个用于机制开发、40 个 dev、60 个冻结 test。按业务模板及数据实体划分，近似改写不得同时出现在 dev 和 test。

| 桶 | 建议数量 | 必须覆盖的样例 |
| --- | --- | --- |
| 基础内容决策 | 20 | 明确需求、模糊兴趣、文章入口、信息不足但可先帮助 |
| 多轮状态/记忆 | 25 | 用户换城市、改日期、儿童年龄变化、旧偏好冲突、清空记忆竞争 |
| 检索/来源 | 15 | 空结果、软条件放宽、地区硬过滤、同名文章、恶意文章文字 |
| 行程可行性 | 15 | 重叠、闭馆、跨午夜、未知开放时间、路线失败、局部重规划 |
| 酒店报价 | 15 | 同口径价差、税费缺失、儿童政策未知、过期/变化、同名不同 ID |
| 内容运营 | 10 | 原文诊断、草稿、未确认写入、版本冲突、确认后重复请求 |
| 恢复/预算 | 10 | 超时、429、断流、重启、取消与迟到结果、预算耗尽 |
| 身份/攻击 | 10 | 跨用户计划/证据、伪造来源、工具文字要求越权、错误角色 |

每条样例包含：输入轮次、初始状态、fixture 版本、允许来源、环境故障、硬条件、必需事实、可接受行动集合、禁止副作用、预期最终状态和评分 rubric。不同合法工具路径可以都通过，不把某一条固定轨迹当作唯一正确答案。

真实地点条目若用于业务样例，必须记录其授权与来源；纯机制测试可用虚构节点。虚构酒店和价格显式标记，避免对实际商家形成错误事实陈述。

## 4. 指标定义

### 确定性主指标

| 指标 | 定义 | 为什么必要 |
| --- | --- | --- |
| Task success | 满足该样例所有必需输出、硬条件和副作用限制的任务数 / 适用任务数 | 防止语言流畅掩盖未完成 |
| Hard constraint adherence | 明确硬条件没有被静默改变且结果满足的任务数 / 适用任务数 | 防止给错误城市/日期/预算 |
| Evidence coverage | 需要来源的事实中，有合法且支持该字段的证据数量 / 此类事实数量 | 引用存在不等于引用支持 |
| Fact correctness | 在可核验事实中与 gold 一致的数量 / 可核验事实数量 | 识别价格、政策、名称错误 |
| Unknown handling | 缺失或冲突样例中正确显示未知/冲突并避免断言的数量 / 适用样例数量 | 避免“查不到就编” |
| Unauthorized side effects | 未授权/未确认/越权的写入次数，及受测攻击样例数量 | 高风险失误单独报告 |
| Tool validity | 满足 schema、前置条件和权限的工具调用数 / 总调用数 | 定位工具选择问题 |
| Recovery success | 故障任务中恢复或正确部分退出的数量 / 故障任务数量 | 明确恢复与降级是否成功 |
| Retrieval quality | 有 gold 的检索任务 Recall@k、nDCG@k，并单报硬过滤违规 | 评价召回与排序 |
| Cost / latency | 每任务模型+工具用量、估算成本、端到端 p50/p95 | 控制能力代价 |

必需信息缺失时，正确发起澄清可以是阶段成功，不能同时统计为完整行程成功。供应商不可用时，正确降级属于 resilience success，与完成实时酒店搜索分开。

只报“成功率”不够：同时报告分子、分母、样本数、桶、未适用项、拒绝/降级比例。不能通过不回答困难任务把事实准确率人为抬高。

### 人工 rubric

相关性、建议取舍、解释可理解性、澄清必要性、行程可操作性，各 1–5 分，明确例子与评分锚点。人工评审看匿名化输出和来源，尽量不知道系统组别。对存在分歧的样例保留理由与仲裁记录。

可用 DeepSeek 作为辅助 judge，但先用人工样本校准，固定 rubric/version；不能把同一模型的自评当作唯一证明。涉及权限、金额、日期与真实写入，优先代码/数据库检查，不交给 judge 决定。

## 5. 基线与公平比较

| 组 | 配置 | 检查的能力 |
| --- | --- | --- |
| B0 | 同一模型，只有用户请求和明确给定的上下文，不调用工具 | 纯模型能做多少，哪里因缺资料无法完成 |
| B1 | 固定一次检索 + 回答，无动态工具循环/持久状态 | 普通 RAG 的能力边界 |
| B2 | 完整单 Agent + 工具/状态/验证 | Agent 机制的基础价值 |
| B3 | B2 + 分层记忆 + 受限委派 + 恢复等完整配置 | 增量复杂度的收益与代价 |

B0/B1 与 B2 的信息取得方式不同，因此能力差异不能全归因于“推理更好”。另做一个**等信息子集实验**：将同一份合法候选/事实提供给各组，只比较选择、约束遵循、结构化输出与解释。

消融才是解释机制收益的主要证据：从完整系统每次关闭一个机制，保持模型版本、提示核心、fixture、可用数据、最大预算、测试集与故障注入一致。

| 消融 | 观察什么 | 需要说明的边界 |
| --- | --- | --- |
| 关闭委派 | 复杂行程完成率、成本、延迟 | 等总预算比较；多一次模型调用不天然更优 |
| 关闭长期记忆 | 返回用户澄清次数、偏好适配、错误沿用 | 用户第一次使用不应凭空收益 |
| 关闭压缩 | 长会话成本、上下文遗漏 | 短会话不是充分测试 |
| 关闭检索重排/放宽 | Recall、地区违规、空结果率 | 不许放宽硬条件来提高召回 |
| 关闭证据补全/validator | 伪造事实、预算和时间错误 | 仅离线 fixture 隔离运行，不影响正常产品约束 |
| 关闭 checkpoint/幂等 | 故障恢复、重复写入 | 在测试数据库中运行，不造成真实副作用 |
| MCP 与直接调用对照 | schema、结果一致性、延迟/异常 | 标准化不必然提高规划质量 |

运营 Agent 单独评测诊断与草稿；不拿游客任务作为其成功率分母。

## 6. 运行方法

- 固定 repo/data/prompt/schema/provider/model 版本、温度/推理参数与价格快照；记录开始时间与配置。
- 每组 test 至少运行 3 次，报告均值及波动；fixture 结果固定，模型输出仍可能变化。
- 批量执行限制并发和总预算；评测用量与产品用量分账。
- 每轮保存 redacted 输入、工具动作、来源引用、状态 patch、校验结果、最终输出及用量，不保存禁止留存的供应商内容。
- 故障注入使用 deterministic trigger，例如某个工具第一次 timeout、某步之后 worker 重启；各组条件相同。
- 测试集在版本冻结后验收。调优用 dev；因测试发现失败而修复后，明确这是新的系统版本，并保留旧报告。

建议命令接口（未来自有脚本，不是现在已存在的命令）：

```text
python -m eval.run --config eval/configs/single_agent.yaml --split test
python -m eval.compare --runs <run_ids> --output <report_dir>
python -m eval.faults --suite recovery --data-mode fixture
```

## 7. 建议验收门槛

门槛在 P0 固定样例后可调整一次并记录理由。下表是初始建议，不是性能承诺：

| 项目 | 建议门槛 |
| --- | --- |
| 关键领域/权限/事务回归 | 所有指定必过用例通过；不存在未确认内容发布、跨用户读取或重复本地写入 |
| fixture 硬条件、ID 与事实卡片约束 | 必过集合全部通过；不能静默改变城市/日期/预算，不能输出不存在报价 |
| 完整 task success | 冻结 test ≥85%，并分桶报告，不用总平均掩盖关键失败 |
| 缺失/未知处理 | 适用 test ≥95%；关键金额/政策缺失必须显示未知 |
| 故障恢复/正确降级 | 故障集合 ≥90%；重复写入、旧任务覆盖新状态为必过项 |
| 人工相关性/解释 | 预先定义样本平均 ≥4/5，报告分歧和低分样例 |
| 委派默认开启 | 至少在目标复杂任务上有清楚收益，且符合总预算；否则保留开关默认关闭 |
| 成本/延迟 | 每任务和整套评测不超过预先配置预算；报告 p50/p95，具体时限在 P0 实测后设定 |
| 真实供应商接入 | 只有拥有权限、对应协议验证及受控 smoke 证据才标 connected；fixture 通过不能替代 |

“全部关键回归通过”只说明这个版本在这个集合上通过，不表示未来永不出错或现实服务零风险。任何越权写入都应阻止该版本验收，先修复再回归。

## 8. 三套演示及失败案例

1. 游客决策：文章入口 → 澄清 → 候选与比较 → 约束行程 → 条件改变 → 保存/恢复。
2. 内容运营：覆盖诊断 → 原文依据 → 修改草稿 → 聊天同意不执行 → UI 确认 → 版本冲突/重试。
3. 工程恢复：供应商 timeout → 部分结果 → SSE 重连 → worker 重启 → 新请求取消旧任务 → 无重复写入。

每套演示同时展示一个正常结果和一个失败/未知结果。开发调试页呈现 trace、预算、证据和 guardrail 结果；普通用户界面只展示需要理解的业务状态。

## 9. 最终证据包

交付包含：版本化任务集、运行配置、模型/接口兼容性报告、自动评分与人工记录、基线/消融报告、代表性成功及失败 trace、ADR、上游复用清单、启动说明和可复现实验命令。

项目说明可以写已验证的实现与实验结果；如果没有真实用户/经营数据，不写 CVR、收入或生产效率提升。真实反馈后也需说明样本、对照与观察周期，不能用原型测试替代商业效果。
