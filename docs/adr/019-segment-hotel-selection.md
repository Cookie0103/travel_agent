# ADR-019：住宿段选择使用规范报价引用

状态：接受（2026-10-11，用户明确要求按段选齐后规划）。

## 背景

现有多城市住宿结构已支持 `hotel_stays`，但酒店展示将不同日期的报价合并比较，选择单卡立即发送自然语言规划消息。模型容易漏填其他住宿段，且报价 ID 和证据 ID 不能互换。只改变卡片排版不能补上这个流程缺口。

## 决定

- `HotelPresentation` 在多城市时增加可省略的住宿段元数据：城市、入住/退房、对应证据 ID、段内比较、该段乐天入口；完整卡片仍只有一份。单城市不输出新字段。
- 页面按住宿段各展示约三家酒店；缺少候选的段仍显示，不能把它当已选择。所有需要过夜的段各选一家后，再一次提交规划；零晚段不要求酒店，重访同一城市分别选择。
- 消息可携带 `expected_revision` 和完整 `hotel_stays`；服务端在原会话锁与提交事务里校验归属、时效、条件、住宿段完整覆盖。选择字段仅保存到已有 `request_details` 侧列，带来源 run/revision，无表迁移。
- 结构化选择按日期排序写成确定的消息附注，纳入现有 prompt/mode 幂等比较；相同消息重放先返回原执行，不因之后报价过期而重新运行或收费。
- 酒店展示后的待办标记等待完整住宿选择；SDK 工具边界阻止初始多城市住宿规划越过选择步骤，Stop hook 不再催促该阶段立即规划。已有草稿/正式行程修改继续沿用原住宿。
- 服务端业务上下文提供该轮规范选择。现有校验/暂存复用一个规范化函数：只在同 run/revision 且模型漏填住宿字段时补齐；显式不同或清除被拒绝并提示采用用户选择。正式保存与恢复继续使用草稿内容及原校验，不放宽证据、住宿或硬条件规则。
- 选择不自动订房；乐天另页仍需用户选日期和人数。页面状态过期/旧 revision 禁止提交，服务端再次裁决。
- 酒店展示按住宿段各保留原 24000 字输出容量；最多六段、十八报价，其他工具和单城市容量不变。完整链接九卡实测约 48929 字，原容量或按六卡批次的 48000 均不足；仍保留有界输出及 512 KiB 模型请求边界。

## 方案取舍

采用小范围结构化输入与已有侧列，避免依赖自然语言里的 UUID 或新增选择表/迁移。拒绝只调整 CSS 后立即规划的方案，也不新增模型循环、运行时或依赖。

## 后果与验证

旧输入与单城市读写兼容；新展示字段对旧读者可忽略。需真实 PG 测试选择覆盖、外部证据/错日期/过期、消息幂等、模型漏填/清除/更换及保存恢复；浏览器验证未选齐不发送和三段独立乐天入口。多段展示仍须守住工具输出字数和 512 KiB 模型请求边界。
