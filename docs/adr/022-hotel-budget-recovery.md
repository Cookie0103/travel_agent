# ADR-022 酒店检索诊断与经确认的预算放宽

日期：2026-10-14。依据：[本批T4与D8](../plans/2026-10-13-interaction-memory-eval.md)。状态：实施。

默认排序只覆盖第一页，原limit在逐晚核价前截断，住宿预算也没有参与筛选。空结果可能来自覆盖、房型、未知价格、异常低价或预算，不能一律归因于用户预算。

复用既有Rakuten.price、逐晚核价和Evidence，不新增报价表。预算存在时核实返回页候选完整总价，按15家批量核价，再预算排序和limit；默认搜索最多一次价格升序首晚发现自救。两次限制只针对首晚发现，后续核价和瞬时失败重试独立计入原计数。默认档为S1预留每段一次额度，仍受每日上限和工具deadline约束。

S1已核实报价在1.5、2、3倍档依次筛选，首个非空档最多3家，不逐档查询。未知价、儿童未知计价、不完整多晚总价不进入档位；只有下限不放宽。total预算按全程房晚统一换算，不能各住宿段重复花整份预算。每日配额不足保留已核实S0并记录skip；不将部分晚金额冒充完整总价。

放宽只提出方案。复用ADR-021卡与消息事务，卡绑定金额、版本、归属及报价TTL；不同上限的卡不合并。只有结构化accept或用户表单明确变更才能改条件；keep、无关revision更新不能让模型代改预算。接受全程共享上限后报价保持有效，TTL过期才刷新。单城旧hotel引用、多段hotel_stays及酒店选择提交均拦截未接受超预算。

价格和诊断保存在既有会话Evidence展示元数据；空结果诊断随presentation保存。计数明确口径，供应商原文和密钥不入日志。离线路径使用同一预算评估函数，固定诊断文案由服务端生成。保留公共search旧签名，诊断入口单独扩展，避免破坏原adapter消费接口。

后果：完整候选核价可能消耗更多逐晚配额，不足则总价未知并解释原因；第一页检索不能证明全城没有酒店。旧“超预算只是提醒”断言与V2冲突，例外待D10，不通过改断言假装过关。

2026-10-14 F1：用户选择保持后，同session/条件版本/放宽金额不再创建可点击卡；拒绝只针对该金额，不同金额或用户改条件后允许重提。原报价仍须按当前正式预算校验；旧已回答卡历史保留。

> 2026-10-19 补充：用户明确决定，超预算酒店报价不再是草稿的硬冲突。校验码 `hotel_over_budget_unaccepted` 降为 `unknown`（警告，文案含超出额与百分比），不阻止确认保存；预算放宽卡流程保留但不是确认前置条件。详见 docs/plans/2026-10-19-ask-less-flow.md“第三轮”。
