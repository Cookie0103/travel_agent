## 1. 现状事实（REASONED）

### 1.1 会话与身份
- `users` 表只有 `display_name`、`token_hash`、`token_expires_at`（24 小时）、偏好；没有邮箱/外部账号（`backend/persistence/models.py`）。
- `POST /demo/login` **每次都新建一个用户**（`backend/services/sessions.py:create_demo_user`），令牌只存在前端 `sessionStorage`。关掉标签页 = 永远失去这个用户下的所有会话。
- `sessions` 表只有 `id, user_id, created_at`。没有标题、更新时间、归档标记。
- `GET /sessions/{id}` 只返回 `session_id, created_at`。**没有列出会话的接口。**
- `plans.session_id` 是 `unique`：**一个会话 = 一次旅行 = 一份行程**（含历史版本和草稿）。这个模型对"继续聊同一趟旅行"是对的，无需改。

### 1.2 对话历史其实已经落库
- `task_runs` 保存每条用户消息的 `prompt`、模型 `answer`、`status`、`mode`、`created_at`；`run_events` 保存每次运行的事件，`presentations(db, run_id)` 已能取出该次运行展示过的卡片（`backend/persistence/runs.py`）。
- 所以"读取历史消息"大部分是把现成数据按会话串起来，不需要新存储。
- 跨天续聊时 Agent 看到的上下文：SDK 续接依赖本机私有 transcript 文件与指纹（`providers/claude_agent/checkpoints.py`），失效时会退回 `business_snapshot`（旅行条件、行程、证据来自数据库）。另外 `recent_completed` 只带最近 **2** 轮已完成对话（`persistence/runs.py`）。含义：隔天续聊"业务状态不丢，但聊天措辞记忆很短"。可接受，但要在产品文案里诚实。

### 1.3 "京都"耦合点
硬类型（`Literal["京都"]`）：`domain/catalog.py`（Place、Article）、`domain/hotels.py`、`domain/travel_request.py`（`TravelConditions.city`）。
逻辑耦合：
- `domain/catalog.py:search` 把 kyoto/京都/京都市 归一为"京都"；
- `domain/validator.py:88` 用 `request.city != place.city` 判定冲突；`domain/hotels.py:91` 同理用于酒店；
- `agent/persona.py`：系统提示词明确"用户指定京都以外的地区 → 拒绝并询问是否改京都，不调用工具"；
- `agent/demo.py:82`：离线演示"仅覆盖京都二至三日游"；
- `domain/itinerary.py`、`tools/travel.py`：提示语写死"京都当地时间 +09:00"；
- 前端 `components/conditions.tsx` 提交时写死 `city: "京都"`（本次前端改造要带上这条）。
- 契约：`data/contracts/web-openapi.json` → `apps/web/src/lib/api-types.ts`（生成，需重导）。
- 仓库里含"京都"的文件超过 40 个；测试里约 25 个文件引用京都（REASONED，按 grep 计数）。

### 1.4 数据层是"一个城市的小样本"
- `data/snapshots/osm.json`（OSM 快照）、`wikivoyage.json`（一篇攻略）、`data/fixtures/hotels.json`（**12 条虚构房价**）、`data/fixtures/routes.json`（**8 条手工写的两点间路段**）。

- 酒店走 `adapters/supplier.py` → `mock_supplier/`，这是接真实供应商的现成接缝。

## 4. 第 3 层：真正的多城市串联行程（B4c）

"京都 2 晚 → 神户 1 晚 → 大阪 2 晚"：
- `TravelConditions.city` 是**单值**，`start_date/end_date` 是一段。需要 `stays: [{city, start_date, end_date}]` 之类的结构，或按天标注城市。
- 受影响：`invalidated_kinds`（改任一段只失效该段的报价）、`validator.py`（按日期归属到对应城市再检查）、`domain/hotels.py` 与酒店服务（每段单独报价与比较）、预订（每段一个暂留/订单，幂等键与 `bookings` 的 `UNIQUE(session_id, evidence_id)` 需要复核）、行程视图与前端卡片、城市间移动的路线估算。
- `travel_requests.conditions` 是 JSONB，需要写**向后兼容解析**（旧的 `city` 单值自动转为单段 `stays`），否则存量会话读不出来。
- **估算 4–7 天，风险高**（核心域模型变化 + 真实 PG 回归面大）。
- 便宜的折中（可以替代它）："区域"模式——`region=关西`，地点可来自区域内任一城市，仍只有一个住宿基地，验证器放宽为"区域内"。约 1–2 天，能覆盖"以大阪为基地逛京都、神户、奈良"这类最常见诉求。**建议先做折中。**

## 5. 第 4 层：真实数据与 OTA

### 5.1 "自己去调查"
现在的证据链是"带版本的历史快照 + 来源署名"，这是刻意设计（`persona.py`：不能把快照说成实时）。接实时数据意味着：新增 `data_mode: live` 的工具契约与证据种类、缓存与授权策略、失效规则。
- OSM Overpass：授权友好（ODbL，需署名），但有速率限制，不适合在请求路径里直接打。
- 商业地点服务（如 Google Places）：**服务条款通常限制缓存与再展示（ASSUMED，动手前核对）**，与"证据可回放"的设计冲突。
- 通用网页搜索：事实不可核验，与"每个结论有来源与版本"的产品原则冲突，**不应直接进入行程校验和证据链**；但作为"只读研究工具"是可行的（commerce-agents 就是这么做的，见 §9）：默认关闭、开关控制、结果按第三方不可信数据处理、回答里明确标注"网页信息，未核实"。
- 估算：网页搜索作为只读研究工具约 **1–2 天**（工具开关 + 白名单 + 预算/防护 + 提示词与标注 + 测试；是否能复用 Claude Agent SDK 自带的网页工具取决于 `providers/claude_agent/guard.py` 的白名单机制，**未核实**；DeepSeek 路径没有 Anthropic 的服务端搜索工具，需要自备搜索提供方，**ASSUMED**）。要让搜索结果变成有版本、有来源的证据（可被校验引用）则另算：每类数据源 3–5 天（工具 + 证据 + 测试 + 提示词）。

### 5.2 OTA 预约
- 没有核实过各家 OTA 的接入条件（ASSUMED）：一般认知是——Booking/Expedia/Agoda 的预订 API 需要合作方资格；日本本地的乐天トラベル提供带 App ID 的空房搜索类 Web API，但**通常不支持代用户下单**，只能返回预订页链接。动手前请逐家核实现行条款。
- **用浏览器自动化在 OTA 网站上代下单**：违反多数站点条款、极脆弱、并涉及支付，不建议，也不适合作为面试项目的卖点。
- 现实路线：在 `adapters/supplier.py` 这条接缝上增加一个"真实搜索 + 深链跳转"适配器（带日期/人数/房间参数的预订页链接），**暂留与下单继续用现有模拟供应商**。估算 3–5 天（含密钥管理、限流、失败降级、`data_mode` 标注）。
- 这也符合你之前说的"OTA 付费功能先缓一缓"。

### 值得借鉴到你项目的设计（都是后端层面，和前端重做无关）
1. **会话 = "状态文档 + 对话记录"两部分，带版本号做乐观并发**（`SessionRecord.version`，过期写入被拒）。你的项目已经用行锁解决并发，不必照搬，但"存储接口最小化"的拆法可以参考 B1/B2 的边界。
2. **跨会话长期记忆**与"单次会话状态"分开。你已经有偏好面板（`/preferences`），方向一致；可以考虑让 Agent 在对话结束后提议保存偏好，但现在的设计是"不自动写入"，是有意选择，不建议为了对齐官方而改。
3. **网页搜索按配置开关**，工具清单随配置变化，执行器拒绝未注册名字。
4. **身份只在会话开始时绑定**，之后任何路由和工具参数都不带用户 ID。你的 `identity()` 依赖已经满足这条。

### 不建议照搬的部分
- 官方的会话存储是内存实现、进程重启即丢，仅作演示；你的 PG 持久化已经更强。
- 官方行程由模型每次重绘，不是业务对象；别为了"像官方"去掉你的草稿/版本/锁定。

### 对第 7 节里程碑的影响
- 网页搜索比我之前估的便宜：从"每类数据源 3–5 天"降为"作为只读研究工具 1–2 天"。可以作为 M-D 的第一项，面试叙事价值高（可选、可审计、有防护）。
- M-A（跨天续聊）仍是必做项，而且是**比官方更完整**的地方，值得作为亮点。
