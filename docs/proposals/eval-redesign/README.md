## 0. 一句话目标

> 用 **约 30 道题、每题跑 3 次、单次全量 ≤50 CNY（真实 DeepSeek）**，回答一个问题：
> **同一个模型、同一套系统，面对正常请求和边界请求，能不能稳定、及时、诚实地帮用户做完一份日本行程，并且记住该记住的偏好。**

完成标准（done means）：
- 每道题的"成功"可以由代码和数据库状态客观判定，judge 只负责体验分；
- 报告里能直接看到三样东西：**稳定性（pass^3）**、**等待时间**、**失败原因**；
- 两位真人评分员能复核 judge，一致率达标后，体验分才能进入"成功"判定。

不做的事：不比较模型、不追求 100% 维度覆盖、不做 IRT 选题、不做自动失败归因模型（理由见 research-notes）。

## 1. 现状体检（v0.1 结论）

### 1.1 已有的（不推倒重来）
`eval/` 共 26 个文件，约 6900 行，常用用例约 80 条（V）。已有能力：
- 代码评分：工具选择、禁止工具、终态 DB 子集比对、行程独立重校验、`unknown ≠ pass` 的三态分母（R）。
- `claims.py`：把回答文字和实际事件（卡片、重试次数、报价过期）对账。这是现有框架里最有新意的一块（R）。
- 故障注入：`backend/adapters/evaluation_faults.py`、`mock_supplier/`，在服务端注入，模型看不到（R）。
- 模拟用户 `eval/simulator.py`（8 个场景），以及 pass@1 / pass@k / pass^k（`eval/report.py:199-205`）（R）。
- Langfuse：OTel span 加数值 score（`backend/adapters/tracing.py:153`）（R）。

### 1.2 主要问题
| # | 问题 | 证据 |
|---|---|---|
| P1 | **工程量远超题量**：重评分、triage、发布、校准等周边代码远大于评分核心（`graders.py` 107 行） | R |
| P2 | **体验几乎没测**：`response_rule` 是正则，"追问澄清"只要回答带问号就通过；judge 未校准、不进门槛，真人评分为 0 条 | R，`docs/execution/verification.md` |
| P3 | **模拟用户太配合**：人设只有一句"简短耐心的旅行用户"（`eval/simulator.py:375`），没有拟真度检查。Sim2Real Gap（COLM 2026）表明这会让分数虚高 | R + 论文 V |
| P4 | **等待时间没进门槛**：只有 `first_progress_seconds`，没有时间预算，没有"用户放弃" | R |
| P5 | **记忆链路断了一截**：提取有代码判分；但落库到 active 只有 2 个模拟场景；"新会话注入"检查的是服务层快照，不是实际发给模型的 system prompt；行为只用正则找"特种兵"；床型没有用例 | R |
| P6 | **每类只有 1–3 题**，k=3 下统计意义很弱；legacy、frozen、v2 三套并存 | V（数量） |
| P7 | **工具轨迹只看集合**，大部分参数正确性判为 unknown | R |

### 1.3 和负责人的取舍对齐
负责人明确的产品取舍：**宁可快一点给出能用的方案，也不要让用户等 3–5 分钟**；约束不必一次全满足，可以靠后续对话改善。测评必须体现这一点。结论是：约束要分级（第 4 节），时间要进入成功判定（第 3 节）。

## 2. 测评怎么做（a）

### 2.1 总体形态
```
30 道题（任务 = 初始状态 + 模拟用户脚本 + 判定规则）
  × 每题 3 次（每次新用户、新库、新会话）
  → 本地后端 + 真实 DeepSeek + 真实乐天/Google/天气（故障题在适配器层注入）
  → 每次运行产出：DB 终态、run_events、最终回复文本、耗时
  → 评分：代码判定（成功与否） + judge 体验分（参考） + 少量真人复核
  → 报告：pass^1 / pass^3、Success@T、质量-时延散点、失败分类表
  → 数值 score 推 Langfuse，失败对话由人读
```

### 2.2 两个前沿点（本方案的新意，只做这两个）

**前沿点 1：Success@T，硬/软约束分级，看是否诚实标注**
- 依据：ChinaTravel（ICLR 2026）用代码逐条校验组合约束；*AI Agents That Matter* 主张准确率和成本一起报告（Pareto）；Realtime-Bench（2026-10）按真实时钟计成功率；*False Success*（ICML 2026 workshop）发现 LLM judge 识别"自称完成、实际没完成"的 AUROC ≤0.65。
- 做法：一次运行的成功 = **硬约束全过** ∧ **在时间预算 T 内** ∧ **没有虚假声明**。软约束只计分、不判失败；但软约束没满足又没告诉用户，按虚假声明处理。
- 新意：调研没有找到把"用户耐心/放弃"纳入 agent 测评的近期论文（research-notes §H），这正好是负责人的真实痛点。

**前沿点 2：不配合的模拟用户，并做轻量拟真度校验**
- 依据：Sim2Real Gap（COLM 2026，451 名真人对比 31 个模拟器）发现 LLM 模拟用户过度配合，形成"简单模式"；UserProxyBench 发现模拟用户最常见的问题是一开始就把信息全说完。
- 做法：每道题的模拟用户带脚本：分几轮透露信息、第几轮改主意、耐心上限多少秒；行为由脚本固定，模型只负责措辞（避免 *Persona Following Is Not Selective Control* 指出的属性串扰）。
- 拟真度校验：两位真人各亲手跑 5 道题，和模拟用户在同题上比较三件事：轮数、失败类型、是否放弃。差异大就改脚本。不做复杂指标。

### 2.3 运行环境
- **在本地后端跑**（docker 里的 PG，`eval/database.py` 每次建临时库），保证每次运行环境干净、互相隔离。部署页面（`docs/operations/product-v2.md:67` 记录的 Railway web 地址，可能已变化）只给真人评分员用。
- 真实 API：DeepSeek、乐天、Google、Open-Meteo 都用真实调用（负责人要求）。故障类题目复用现有服务端注入，因为真实 API 无法按需返回 429 或空结果。
- profile 用 `human`（与线上一致：不限工具次数、900 s 超时），**不要**用 `default` 的 16 次工具调用 / 240 s 限制，否则测的不是线上行为（R，`backend/profile.py:28-52`）。需要确认线上实际用的是哪个 profile。

### 2.4 预算（V 的单价 + A 的推算）

| 多轮模拟用户运行 | ≈0.38 CNY/次（V，F12 证据：22 次 8.44 CNY） | 24 题 × 3 | ≈27 CNY |
| 单轮/短对话题 | ≈0.08 CNY/次（V，`verification.md:115`） | 6 题 × 3 | ≈1.5 CNY |

## 3. 评什么：五个维度（d）

只设五个维度，每个维度一两个主指标。指标的数量刻意压低。

| 维度 | 主指标 | 谁来判 | 进不进"成功"判定 |
|---|---|---|---|
| ① 结果正确 | 硬约束通过率；DB 终态符合预期 | 代码 | **进** |
| ② 等待时间 | 首个可用回复时间 TTFUA、每轮总耗时、校验和修复轮次 | 代码 | **不进**（v0.3 起只记录，供分析；负责人决定不设上限） |
| ③ 工具与恢复 | 必需工具被调用、无禁止工具、无编造工具名；故障后恢复或如实告知 | 代码 | **进** |
| ④ 记忆 | 提取 → 落库 → 跨会话注入 → 行为生效，四层分别判 | 代码 | **进**（仅记忆题） |
| ⑤ 用户体验 | 每题 3–5 条 rubric：是否诚实标注、是否重复追问、是否有用、语气 | judge + 真人复核 | **先不进**，校准达标后再进 |

再加一个横向检查：**虚假声明**，即回复里说的和 DB 不一致（"已为你选好酒店"但没有记录、"在预算内"但实际超了）。复用并扩展 `eval/claims.py`，任何一条不一致即失败。

### 3.1 等待时间（v0.3：只记录，不设上限）
- 负责人决定：等待时间不设上限，只记录，用来分析和评估优化效果。题目里默认不写 `patience_s` 和 `ttfua_s`。
- 报告里的 Success@T 表只作参考，表示"如果设上限 T 会怎样"。
- 以下是 v0.1 的原始设想，保留作参考：
- 建议初值（A）：TTFUA ≤ 60 s 为达标；单轮 > 120 s 记为"流失风险"；单轮 > 180 s，模拟用户放弃，本次运行判失败。
- 报告里同时画**质量 × 时延散点**：每个点是一道题的一次运行，横轴是总耗时，纵轴是软约束得分加体验分。一眼就能看出"又慢又好"和"又快又差"的题。
- 单独统计校验-修复循环跑了几轮、每轮耗时多少（来自 `run_events`），用来定位拖慢响应的具体环节。

### 3.2 用户体验 rubric（judge 用）
- 每题只写 3–5 条该题特有的检查项，加 4 条通用项。逐条判"是 / 否 / 无法判断"，不给整段对话打总分（依据 Odysseys：分项评分比整段打分与人类更一致；Anthropic 文章建议给 judge 留"Unknown"选项）。
- 通用 4 条：
  1. 没满足的约束是否告诉了用户（如超预算、营业时间未知）；
  2. 卡片已经问过的内容，没有在文字里再问一遍；
  3. 回复能直接推进下一步（有方案或有明确选项）；
  4. 语气礼貌、简洁，不说空话。
- judge 必须拿到**工具返回原文和 DB 摘要**，不能只看对话（依据 *False Success*）。
- judge 自检（一次性，便宜）：把 rubric 换一种说法重判一遍，看判决翻转率（借鉴 *Policy Invariance*）。翻转率高的条目要改写。
- 真人校准：两位真人对 20 次运行打同一份 rubric。judge 与真人的一致率 ≥ 80%（A，待定）的条目，才能进成功判定。

## 4. 约束分级（结果正确维度的细则）

| 级别 | 内容 | 不满足时 |
|---|---|---|
| **硬约束** | 日期在用户给定范围内；城市对得上（不把京都景点排进大阪那天）；人数/房间数正确；用户明确的房间要求（禁烟、床型）不被违反；酒店、价格、景点必须来自工具返回（有 evidence_id），不能编造 | 本次运行失败 |
| **软约束** | 景点不重复；营业时间已核实；酒店在预算内；节奏符合偏好；路线顺 | 只扣分，不失败；**但如果没满足又没告诉用户 → 记为虚假声明 → 失败** |

依据：负责人的产品取舍（§1.3），加上 ChinaTravel 的逐条约束校验思路。实现上复用 `backend/domain/validator.py` 的 `verified / unknown / conflict` 结果，只需要加一张"哪个检查项属于哪一级"的映射表。

## 5. 题目怎么出（b）

### 5.1 出题原则
1. **约 30 题，深而不广。** 每道题都是多轮对话，覆盖一个完整的边界情况，而不是一句话问答。
2. **每题都能客观判定成功。** 写题时同时写参考答案要点和判定规则。"两位专家看了会得出同样结论"（Anthropic 文章），做不到的题不收。
3. **正例和反例都要有**：既测"该做的做了"，也测"不该做的没做"（不该存的偏好、不该查的酒店、不该编的价格）。
4. **优先来自真实失败。** session log 里已记录的问题直接成题，例如：编造工具名、回复说"特种兵"但面板显示"标准"、卡片问过又在文字里问、多城市选酒店、搜不到酒店、带小孩。
5. **试跑后剔除太容易和太难的题**：3 次全过且没有区分度的，移进回归集；3 次全挂且确认是题目本身有问题的，修题（依据 *Efficient Benchmarking of AI Agents*：只保留通过率居中的题，排名更稳定）。

### 5.2 题目分布（30 题）
| 类别 | 题数 | 例子 |
|---|---|---|
| A 主流程 | 4 | 京都 2 晚两人；京都 + 大阪多城市；带 5 岁小孩；预算很紧 |
| B 信息不全或模糊 | 5 | 不说日期；日期写反；"刚才那家"指代；中日英混写；预算明显不现实 |
| C 用户中途改变 | 5 | 第 3 轮改城市；改日期；拒绝放宽预算；改节奏；撤销已选酒店 |
| D 工具故障或空结果 | 5 | 乐天无房；429 后恢复；超时；景点缺营业时间；天气超过 16 天未知 |
| E 无解或越界 | 3 | 海外目的地；要求真实下单付款；指定一家不存在的酒店 |
| F 记忆 | 6 | 见 5.3 |
| G 对抗 | 2 | 用户试图让 agent 忽略规则；工具返回文本里夹带指令 |

### 5.3 记忆题（负责人特别要求）
记忆题按四层分别判定，每一层都对照 DB 或 prompt，不只看回复：

| 层 | 判定方式 |
|---|---|
| L1 提取 | 本轮产生的 `propose_memory` 提案的 key/value/scope 与预期一致（复用 `eval/memory_metrics.py`） |
| L2 落库 | 模拟用户点"记住"后，`user_memory_facts` 中对应行为 `status=active`、`scope=long_term`；点"这次而已"则为 trip |
| L3 注入 | 新会话里**实际拼装的 system prompt** 包含该事实。需要新增一个仅评测模式下启用的钩子：把 `worker.py:147` 拼好的 prompt 写进私有 `.cache`（现在全链路都不记录完整 prompt，R） |
| L4 生效 | 新会话的行为体现了偏好：长期节奏已知时，询问卡片不再问节奏；行程密度符合节奏（代码判）；回复没有和面板矛盾（judge） |

6 道记忆题：
1. 确认长期节奏后开新会话，验证 L1–L4 全链路；
2. 点"这次而已"，新会话里不应出现该偏好；
3. 改节奏（特种兵 → 轻松）：旧值变为 superseded，新会话用新值；
4. 随口一提或第三方偏好（"我朋友喜欢早起"）：不应提案；
5. 删除偏好后：新会话 prompt 里不再出现；
6. 两个用户隔离：用户 A 的偏好不出现在用户 B 的 prompt 和回复里。

另外有一个记忆层面的设计疑点，需要负责人确认（Q5）：床型、禁烟按规则只对本次有效，不能存为长期偏好（`backend/domain/memory.py` 的 `TRIP_ONLY_PREFERENCES`）。如果负责人期望它们是长期偏好，这是产品问题，不是测评问题。

### 5.4 题目格式
沿用 `eval/cases.py` 的 schema，新增四个字段：
- `user_script`：每轮要透露的信息、改主意的轮次、要点击的选项；
- `patience_s`：模拟用户的耐心上限；
- `hard_checks` / `soft_checks`：按第 4 节分级；
- `rubric`：3–5 条该题特有的体验检查项。

新题放进一个统一的新套件 `eval/cases/v3.jsonl`。旧套件的处理见第 7 节。

## 6. 工具怎么设计（c）

这里的"工具"分两类：agent 调用的业务工具，以及测评自己需要的观测工具。

### 6.1 业务工具的覆盖
agent 暴露 19 个工具（`backend/tools/travel.py:146-292`，`search.py:19-32`，R）。测评不需要逐个工具写题，只要求 30 道题合起来覆盖三条主链：
- **酒店链**：`update_travel_request` → `search_hotel_offers` →（`select_hotel_from_chat`）→ `present_travel_result`
- **行程链**：`search_places` / `get_place_facts` → `estimate_routes` → `validate_itinerary` → `stage_plan_change`
- **记忆链**：`propose_memory` → 确认卡片 → 新会话快照

工具层的判定只做四件事：
1. 必需工具调用了；
2. 禁止工具没调用（例如越界题不应查酒店）；
3. 没有编造工具名（目前会被 guard 直接拦停，`guard.py:191`）；
4. 故障之后，要么自动恢复，要么如实告诉用户，不能装作成功。

**不检查**调用顺序和最优路径。依据 Anthropic 文章："评判 agent 产出了什么，而不是它走了哪条路。"

### 6.2 故障注入
复用现有服务端注入（`EvaluationFault` 9 种，`SupplierFault`）。按 *Bench2Robust* 的思路，每种故障标明"可恢复"还是"不可恢复"：
- 可恢复（429 一次、超时一次）：期望自动重试成功，用户无感知；
- 不可恢复（无房、景点无营业时间）：期望如实说明并给出替代方案。

### 6.3 测评侧需要新增或改造的观测工具（最小集合）

**操作步骤**：
1. 把 [question-generation-spec.md](question-generation-spec.md) 交给 GPT，生成 30 道题，保存为 `eval/cases/v3.jsonl`。
2. 做加载校验（命令见 spec 开头）。报错信息会给出行号和具体字段。
3. 冒烟测试：`uv run python scripts/dev.py eval-v3 --live --trace-cloud --repeat 1 --case-id <一道多城市题> --case-id <一道记忆题>`。跑完检查三处：
   - `.cache/eval-v3/<run>/report.md`；
   - Langfuse 里打了 `v3` 标签的 trace 和 score；
   - `.cache/eval-v3/<run>/transcripts/`。
4. 全量测试：`uv run python scripts/dev.py eval-v3 --live --trace-cloud --repeat 3 --judge-check`。
5. 真人校准：
   - 用 `uv run python -m eval.v3_judge sheet .cache/eval-v3/<run>` 导出评分表；
   - 两位评分员按 transcripts 填写 `rater_a` 和 `rater_b`；
   - 用 `uv run python -m eval.v3_judge agree .cache/eval-v3/<run> <填好的表>` 计算一致率。
   - 一致率 ≥80% 的条目，才考虑纳入成功判定。
6. 阅读失败对话，按 `report.md` 里的失败原因表，决定是修题还是修 agent。

**中断后怎么接着跑**：Ctrl-C、`--max-cny` 到顶、授权失败，或连续 2 个 trial 因限额类错误（`rate_limited`、`service:429`）结束时，运行会停下，已完成的 trial 和报告都保留，结尾打印“接着跑：…”命令。把命令里的 `--resume <run_dir>` 原样跑一遍即可：已完成（成功或真实失败）的 trial 跳过，缺失或带 infra_error 的重跑，报告用全部结果重新生成。题库内容或所选 case-id 变了会拒绝续跑，确认无误再加 `--resume-force`。
