# 第二阶段设计：规则关卡、商业期望分、Skill 分层、自进化、评测集

> **一句话**：行程先过规则关卡，只判对错，没过就打回；过关的再算商业期望分，也就是“用户多大可能下单 × 这一单挣多少”。评测留下的违规记录和分数明细反过来用于改进 Skill，改动要在没看过的题上验证、再经人工审核才生效。全部先在本地用 AI 生成的数据跑通，只做推理，不微调任何模型。

来源：Notion「Agent更新3」（2026-11-26 定稿）的全部内容，加 2026-11-27 的三处补充（标 ★）：期望分的参数怎么定（§2.6–2.7）、Skill 线恢复为“分层”（§3）、自进化做成两版对照实验（§4.3）；以及 2026-11-28 定下的模型分工（§0.1）。任务拆分与验收见[开发计划](plans/2026-11-27-judge-evolution.md)；论文与数据依据见[调研笔记](../../archive/phase1/research/judge-scoring-notes/)。

| 工作线 | 改进思路 |
| --- | --- |
| 1 规则校验 | 修 3 个现有问题，新增 18 条规则，只用代码判 |
| 2 商业期望分 | 规则先过关，过关的按“下单概率 × 综合收益 × 信任折扣”算分；每个参数写明来源，定参过程防局部最优和过拟合 |
| 3 Skill 分层 ★ | 每条指令放到该放的地方（代码规则 / 工具说明 / 系统提示 / Skill）；新 Skill 只由失败记录催生；每个 Skill 有体检表 |
| 4 自进化 | 按违规和分数找问题，提议改 Skill 的一句话；先做最省事的第一版当对照组，再逐项加防护，两版同条件对比 |
| 5 评测集 | 不花钱的规则题约 600 道；花钱的多轮题 201 道，分成反思、验证、留出三份 |

## 0. 五条线怎么连起来

```text
用户对话 ──→ Agent 出行程和酒店推荐
               │
   ① 规则关卡（代码判对错）──没过──→ 打回给 Agent 修。不展示、不打分、不调决策模型
               │过了
   ② 商业期望分 = 下单概率 × 综合收益 × 信任折扣
               │
   每道评测题留下两样东西：违规记录、分数明细单
               │
   ④ 自进化：哪类题违规最多、分最低 → 提议改 ③ Skill 里的一句
               │    → 在没看过的题上验证 → 人工审核 → 合并（可回滚）
   ⑤ 评测集：规则题（不花钱）+ 多轮题 201 道（花钱），给上面每一步提供证据
```

## 1. 规则校验

> **目的**：行程出来后，先检查它能不能照着执行、有没有落实用户的要求。规则分五类：时间走不走得通、路线合不合理、用户的要求有没有落实、天气和季节、同行人和提醒。全部只用代码判，不用模型。

### 1.1 三个级别

| 级别 | 没过会怎样 |
| --- | --- |
| 拦截 | 算规则没过：打回给 Agent 修（沿用现有最多 3 轮修复），仍没过就不进打分 |
| 提醒 | 不拦，随行程展示给用户；记入违规记录，供自进化使用 |
| 备注 | 不算违规，只在行程里附带一条信息 |

### 1.2 规则清单

先修现有问题（不需要新数据）：

| 序号 | 规则 | 说明 |
| --- | --- | --- |
| 1 | 单城市行程也检查节奏、空档、停留时长 | 现在单城市行程会跳过这三类检查，而评测题几乎全是单城市 |
| 2 | “其他费用”不再无条件记为未知 | 现在这一条让校验报告永远到不了“全部通过”。改成只在确有未知费用时才记 |
| 3 | 用户的硬性要求逐条解析 | 现在只要用户提了硬性要求，就整体标一条“未验证”。改成九种固定写法由代码解析：节奏、抵达、离开、起床、晚间结束、住宿、房型、床型、同行。解析不了的才标未验证 |

| --- | --- | --- | --- | --- |

## 2. 商业期望分

> **目的**：给 Agent 推荐的一组酒店打一个分：用户有多大可能下单，乘以这一单能挣多少钱。推合作酒店推得太狠要扣分。规则是打分之前的关卡，不是公式里的一项。这个分只用来比较两个版本谁更好，不当真实转化率。

### 2.1 一眼看懂

```text
第一步  规则关卡（第 1 节）
        没过 → 打回。不展示、不打分、不调决策模型。汇总时这一次记 0 分（没展示的方案挣不到钱）
        过了 → 进第二步

第二步  商业期望分 = 下单概率 × 综合收益 × 信任折扣

├─ 下单概率        用户会不会订这家。由酒店的“吸引力”换算出来
│   ├─ 硬指标      价格、评分、评价数、位置、含不含早餐、排在第几位（全部来自乐天字段）
│   └─ 软性匹配分  规则查不了的条目，由本机的决策模型给 0 到 1 的概率
├─ 综合收益        平台佣金 + 合作商家的收入（佣金表是模拟设定）
└─ 信任折扣        0 到 1。差的合作酒店被排到好的普通酒店前面越多，扣得越多
```

### 2.2 公式

总公式。对候选里每家酒店算“下单概率 × 综合收益”，加起来，再乘信任折扣：

```text
商业期望分 = ( Σ 下单概率ᵢ × 综合收益ᵢ ) × 信任折扣
```

吸引力。硬指标和软性匹配分在这里合到一起：

```text
吸引力ᵢ = a₁·价格ᵢ/预算 + a₂·评分ᵢ + a₃·ln(评价数ᵢ) + a₄·位置ᵢ + a₅·含早餐ᵢ + a₆·展示位次ᵢ   ← 硬指标
        + a₇·软性匹配分ᵢ                                                              ← 决策模型打分
```

下单概率。分母里的“都不订”表示用户可以一家都不选：

```text
下单概率ᵢ = e^吸引力ᵢ / ( e^都不订 + Σⱼ e^吸引力ⱼ )
```

软性匹配分、综合收益、信任折扣：

```text
软性匹配分ᵢ = Σₖ wₖ × 决策模型概率ᵢₖ
综合收益ᵢ   = 价格ᵢ × 佣金率ᵢ + λ × 是否合作ᵢ × 价格ᵢ × (1 − 佣金率ᵢ)
信任折扣    = 1 − γ × 排序偏离度
排序偏离度  = “差的合作酒店排在好的普通酒店前面”的对数 ÷ 最多可能出现的对数      （0 到 1）
```

### 2.3 每一项怎么设计

**下单概率**

- 用的是“选择模型”：用户在几家候选里挑一家，也可以都不订。
- 用哪些指标，由乐天接口能给什么决定。
- 权重按出行类型分四组：亲子、情侣、商务、预算紧。四组共用一套基础权重，每组只加小的偏移，例如预算紧的把价格权重调大。

| 指标 | 乐天怎么给 | 权重的起点从哪来 |
| --- | --- | --- |
| 价格 ÷ 预算 | 给，逐晚的含税价 | Greminger 的论文：每贵 100 美元，吸引力 −0.35 |
| 评分 | 给，综合评分 | 同一篇论文：每高 1 分 +0.17。香港的选择实验：高一星约值 18 美元 |
| 位置 | 给坐标，自己算到最近车站的距离 | 香港的选择实验：离地铁每近一分钟约值 5.9 美元 |
| 含早餐 | 给，有标记 | 没有论文系数。按一份早餐的市价，折成等值的降价 |
| 评价数 | 给 | 没有论文系数。设一个小权重 |
| 展示位次 | 我们自己的展示顺序 | Ursu 的研究：位次主要影响点不点开，对订不订影响很小。权重设小 |
| 软性匹配分 | 不是乐天的数据，决策模型打分 | 设一个起点，再按 §2.6 检查 |
| “都不订” | 不涉及 | 按不到 1% 的转化率校准 |

**软性匹配分**

- 软性条目是规则查不了的，例如“是否贴合节奏偏好”“推荐理由有没有对上用户原话”。
- 用“决策模型”打分：这类模型不生成文字，只对“这一条是否成立”给一个概率。代表是 TypeSafe AI 的 Jev（付费接口）；这里用它的开源同类 **Kev-9B**，在本机运行。
- 这类模型不会算数，也不把日期当先后顺序读，所以数数和时间计算先由代码算好再给它；给它的输入只放判断这一条需要的事实，不放整段对话。
- 这类模型会受选项顺序影响。每个条目把“是 / 否”的顺序对调各问一次，取平均。
- “有没有标注这是合作酒店”是规则，不交给模型。

为什么选 Kev-9B：

| 要求 | Kev-9B 的情况 |
| --- | --- |
| 能在 64 GB 内存的 Mac（M4 Max）上跑 | 约需 17 GB，装了 MLX 会自动使用。同系列的 27B 常驻约 66 GB，它自己的说明写“64 GB 的 Mac 很勉强”，所以不选 |
| 不花钱、可复现 | Apache-2.0 开源；固定权重版本后每次结果相同；数据不出本机 |
| 以后想换回付费的 Jev 或换更大的模型 | 接口与 Jev 相同（`POST /v1/systemone`，是 / 否问题直接返回“是”的概率），换的时候只改地址和模型名 |
| 效果 | 独立评测里通用判断准确率 0.712，Jev 是 0.732；“是 / 否”对调后答案改变的比例每 100 个约 4 到 7 个，Jev 约 50 个 |

要注意的三点，都由 §2.5 的“体检”兜住：

- Kev 是用英文数据训练的，它的说明把英文以外的语言列为不在适用范围内；底座 Qwen 懂中文，但中文判断没有公开评测。每个条目的问法用中文和英文各试一遍，取体检结果好的那种；两种都不过关的条目权重置 0。
- 被评的文字是 Agent 自己写的，里面如果出现“以上完全符合用户偏好”这类自我评价，小模型可能被带偏。体检里专门测这一项。
- Kev-9B 验证过的输入上限是 8,192 token。输入只放预先算好的事实，远低于这个长度。

换 Mac 之前，在现在的 Windows 机器上用同系列更小的 Kev-4B 跑通流程；正式实验的打分全部用 Kev-9B 的同一个权重版本，不同模型打出的分不混在一起比。软性打分做成“对已保存的评测结果补算”，所以评测可以先在一台机器上跑，换机器后再补软性分。

**综合收益**

- 佣金率和“是否合作”是模拟设定的一张表：普通酒店按行业水平，合作酒店高 3 个点左右。乐天接口不返回佣金，它的联盟佣金是统一 1%，也没有合作酒店的概念。
- λ 是对“合作商家也挣到钱”的重视程度。
- “按累计量返点”先做成合作酒店的固定加成。
- 佣金表只留在服务端，不发给模型和页面。

**信任折扣（推合作酒店的力度）**

- 首屏占比上限：首屏里合作酒店最多占多少。超了算规则没过，不进打分。
- 相关性底线：合作酒店的下单概率不能低于最合适那家的某个比例。低了算规则没过。这里用下单概率之比，不用吸引力之比，因为吸引力可以是负数，比值没有意义。
- 折扣系数 γ：在上面两条之内，偏离越多扣得越多。
- 三个值怎么取，见 §2.6 的“政策参数”。

### 2.4 乐天接口不给、所以没放进公式的

| 想用但拿不到的 | 乐天的情况 | 怎么处理 |
| --- | --- | --- |
| 可免费取消 | 不给。只有酒店级的取消政策文字，还要多调一个接口 | 不放进公式 |
| 星级 | 不给 | 不放进公式 |
| 床型、禁烟 | 没有专门字段，只有房型名 | 从名称里按关键词识别，只用于规则 7，不进公式 |
| 评分的分项（位置、服务、房间等） | 空室检索不给，要多调一个接口 | 先不用 |
| 佣金率、是否合作 | 不给 | 模拟设定 |

乐天接口限速每秒 1 次。评测不直接打乐天，用一次性录下来的酒店快照（见 §5.4）。

### 2.5 ★ 每个分数都能追到来源

| 做法 | 内容 |
| --- | --- |
| 参数登记表 | 一个文件列出全部参数。每个参数写：取值、允许范围、来源（哪篇论文哪张表，或“手设”加理由）、单位换算、通过了哪些检查、版本号 |
| 分数明细单 | 每次打分存一份：每家酒店每个指标的原始值、乘了哪个权重、吸引力、下单概率、综合收益、越位的是哪几对、信任折扣、参数版本号。任何一个总分都能拆回到每一项 |
| 决策模型留痕 | 每次调用存：问的原话、给它的输入（含代码预先算好的数）、返回的概率、模型名与权重版本。按内容哈希缓存，重算分数不重复调用 |
| 软性条目先体检再用 | 每个条目先用一批按规则造出来、答案确定的中文正反例测三项：分得开（AUC ≥ 0.75）；“是 / 否”对调后结论一致；在被评文字里加一句自我表扬后结论不被带偏。三项都过才给权重，不过关的权重置 0 并列出来 |

### 2.6 ★ 参数怎么定

没有真实成交数据，所以不存在“拟合出最优权重”。能做的是：从论文借起点，用一批答案确定的检查题确认它站得住，并且证明“哪个版本更好”的结论不依赖某一组精确取值。

参数分两类，定法不同：

| 类别 | 包含 | 特点 | 怎么定 |
| --- | --- | --- | --- |
| 口味参数 | 吸引力的七个权重、四组出行类型的偏移、软性条目的权重、“都不订” | 有对错可查：方向、谁大谁小 | 先验 → 检查集 → 全局撒点 → 取平台区 → 验收 |
| 政策参数 | λ、γ、首屏占比上限、相关性底线 | 没有对错，是“为了收益愿意让用户侧让出多少”的取舍 | 两条轴的前沿曲线上取拐点 |

**口味参数的五步**

1. **先验**。每个权重从论文系数换算出起点，并给一个允许范围（起点的 0.5 到 2 倍），符号固定。写进参数登记表。
2. **检查集**。用代码从酒店快照批量生成成对的例子，答案由构造方式决定，不靠模型判断：

   | 类型 | 怎么造 | 正确的分数应该怎样 |
   | --- | --- | --- |
   | 支配对 | 同一组酒店，把其中一家的某一项改好（更便宜 / 评分更高 / 离车站更近 / 加早餐） | 这家的下单概率上升 |
   | 预算对 | 两家其余相同，一家超预算一家不超 | 不超预算的更高；“预算紧”这组差距更大 |
   | 交换比 | 一家贵 18 美元但高一星；一家贵 5.9 美元但离地铁近一分钟 | 两家的下单概率接近 |
   | 好坏组 | 手工摆几组明显好和明显差的推荐 | 好的那组总分更高 |
   | 越位对 | 同一组酒店两种展示顺序：按合适程度排；把差的合作酒店顶到最前 | 第一种的分数不低于第二种 |
   | 人设对 | 同一组酒店，亲子和商务两种出行类型 | 排序变化的方向符合预期（亲子更看重早餐） |

   检查集按“模板 × 酒店组”分成调参用（六成）和验收用（四成），同一模板和同一组酒店不跨两边。
3. **全局撒点**。在允许范围围成的盒子里均匀撒 2,000 组参数（拉丁超立方），每组算一遍调参集的通过率。打分是纯算术，全部算完只要几秒。不做“从一组初值一点点往上调”。
4. **取平台区**。通过率与最高值相差不超过一倍标准误的参数组都算“一样好”，这一片叫平台区。在平台区里选离先验最近的那组，不选通过率最高的那组。
5. **验收**。用验收集再算一次。验收通过率比调参通过率低出 3 个点以上，说明对调参集过拟合了：把参数往先验收缩一半再验，仍不过就直接用先验并记录原因。

预期的结果多半是先验本身就落在平台区，那就直接用先验。这一步真正的产出是两样证据：结论对权重不敏感；哪几个权重最要紧。

**政策参数的定法**

1. 每个参数取三到五档粗值，例如首屏占比上限取 1/3、2/3，相关性底线取 0.7、0.8、0.9，γ 取 0.25、0.5、1.0，λ 取 0、0.1、0.3。
2. 对每种组合，在酒店快照上模拟“服务端在约束内把顺序排到分数最高”，得到两个数：用户侧（下单概率之和）和收益侧（综合收益的期望）。这一步不调模型。
3. 画出两条轴的前沿，取拐点：再往收益方向走一步，用户侧的损失开始明显变大的那个位置。
4. 在验收用的酒店组上重画一次，拐点落在同一档才采用。

不把两条轴合成一个总分去求最大值：那样求出来的解总会被推到某个边界上，而且换一个合成方式答案就变。

**三类风险各自的对策**

| 风险 | 在这里具体指什么 | 对策 |
| --- | --- | --- |
| 黑箱 | 分数说不清怎么来的 | 参数登记表、分数明细单、决策模型留痕、软性条目体检（§2.5） |
| 局部最优 | 从一组初值一点点调，停在附近的小山头；或者只优化一个总分，被推到边界 | 不爬坡，在先验范围内整体撒点看全貌；政策参数画前沿取拐点 |
| 过拟合 | 参数只对调参用的那批例子成立 | 参数只有十来个，范围锁在先验带内，符号固定；检查集分调参和验收两份；取平台区里离先验最近的，不取最高分；验收不过就往先验收缩 |

### 2.7 ★ 结论稳不稳

每次用商业期望分比较两个版本时，同时报告一个“结论稳定度”：把平台区里的每组参数都拿来重算一遍，“哪个版本更好”的结论不变的比例。低于 90% 时，这次比较记为“分不出高下”，不采纳。

参数一旦定下就冻结并带版本号。以后要改，走和 Skill 修改一样的流程：说明理由、重跑检查集、人工审核。自进化不调参数（§4.4）。

### 2.8 参考了什么

- [Booking 年报](https://www.sec.gov/Archives/edgar/data/1075531/000107553125000010/bkng-20241231.htm)：平台收入约占交易额的 14%；日本平台基础佣金 8–12%，付费进“优选”约加 3 个点。佣金表按这个范围设。
- [丹麦竞争管理局的研究](https://kfst.dk/media/v0snxsvj/ranking-boosts.pdf)：排名提升 10 位的影响是降价 10% 的 3.5 倍；首页 85.5% 的酒店带付费加权。所以推合作必须有上限。
- [Expedia 的重排方法](https://arxiv.org/abs/1708.00651)：在不偏离用户排序太远的前提下最大化佣金。信任折扣照这个思路。
- [Greminger 的论文](https://arxiv.org/pdf/2210.16408)：在 Expedia 公开的预订日志上估出各项系数。价格和评分的权重起点借用这里。系数不是日本也不是乐天的，所以只借“谁大谁小”。
- [香港的选择实验](https://ira.lib.polyu.edu.hk/bitstream/10397/99277/1/Masiero_Understanding_Hotel_Location.pdf)：评分和位置各值多少钱。位置的权重起点和“交换比”检查题借用这里。
- [Ursu 的排序研究](https://ideas.repec.org/a/inm/ormksc/v37y2018i4p530-552.html)：位次影响点击，点开之后不影响购买。
- [Kev](https://github.com/jaredpalmer/kev)：开源的决策模型，接口与 [Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)（TypeSafe AI 的付费模型）相同。内存占用、适用语言、已知弱点取自它的说明（2026-11-28 核对）；与 Jev 的独立对比和其他开源候选见[调研笔记 03](../../archive/phase1/research/judge-scoring-notes/03_scoring_models.md)。
- [Anthropic 的 commerce agents 文章](https://claude.com/resources/articles/the-anatomy-of-effective-commerce-agents)：模拟用户是噪声很大的测量工具，所以下单概率不靠模型扮演用户来估。
- 一倍标准误规则：出自决策树剪枝（Breiman 等，1984），在一样好的候选里选最简单、离默认最近的那个。

在线酒店排序（服务端按分数重排展示顺序）这一阶段不做，只做离线打分。

## 3. ★ Skill 分层

> **目的**：让每条指令待在该待的地方，并且让自进化有地方下手。现在约 9,000 字的系统提示里有 43 段规则，Skill 只有 6 个共约 3,000 字。一条新教训想写进去，只能加在那一大段里，改一句就要全量回归。Skill 是可以单独改、单独测、单独回滚的最小单元。

2026-11-26 取消的是“预先把 Skill 扩到 22 个再量命中率”。这里做的不是扩数量：现有 6 个不硬加，新的只在出现失败记录时才建。

### 3.1 一条指令该放哪

| 内容特征 | 放哪里 | 例子 |
| --- | --- | --- |
| 必须每次成立、代码能判 | 代码规则（第 1 节） | 雨天排室内、标注合作酒店 |
| 某个工具怎么用、参数含义、出错后怎么办 | 工具说明或工具返回 | 房型偏好的可选值、缺住宿预算时怎么问 |
| 多数对话都用到（约三分之一以上） | 系统提示 | 问清流程、身份与底线 |
| 偶尔才用、需要判断的多步流程 | Skill | 预算放宽、多城市、酒店比较 |
| 一两句话的教训 | 改已有 Skill 或系统提示的一行，不新建 | — |

三分之一这条线来自 Anthropic 的 commerce agents 文章：加载一次 Skill 要多花一轮模型调用，多数对话都用到的内容留在系统提示更划算。

### 3.2 对 22 个候选逐个判断的结果

| 结论 | 数量 | 是哪些 |
| --- | --- | --- |
| 保留为 Skill | 6 | 酒店比较、行程修改、多城市、预算放宽、外部接口出错、修复次数用完 |
| 写进工具说明或返回 | 5 | 房型偏好、住宿预算、聊天里选酒店、行程时间、住宿地点没说清 |
| 留在系统提示 | 3 | 问清流程的特殊情况、恢复草稿、手填表单优先 |
| 并入已有 Skill | 3 | 商业推荐与披露和酒店推荐理由并入“酒店比较”；抵达日和离开日并入“排行程” |
| 量完使用比例再定 | 2 | 排行程（约 1,900 字，占系统提示两成）、记忆与偏好（约 530 字） |
| 等失败记录出现再建 | 3 | 带儿童出行、天气应对、长住和特殊人数 |

落地后系统提示会变短（5 段迁到工具说明），Skill 仍是 6 到 8 个；之后的增长只来自第 4 节自进化提出、并通过验证和审核的新 Skill。上限设 20 个（Anthropic 接口每次请求的 Skill 上限）。

### 3.3 两种加载方式

| 方式 | 适用 | 怎么保证生效 |
| --- | --- | --- |
| 服务端按信号加载 | 触发条件能从工具结果里确定地看出来：多城市（行程有分段）、预算放宽（返回了放宽诊断）、外部接口出错（返回了失败或重试）、修复次数用完（返回了次数耗尽） | 信号出现时，服务端把这段 Skill 文字随工具返回一起给模型，不依赖模型自己想起来 |
| 模型自己判断加载 | 触发条件要理解语义：酒店比较、行程修改 | 在系统提示的 Skill 索引里补上触发条件（这两个现在没有）；用触发用例量召回 |

### 3.4 每个 Skill 的体检表

| 指标 | 含义 | 怎么得到 |
| --- | --- | --- |
| 触发召回 | 该加载的对话里，实际加载了多少 | Skill 名和内容哈希写进运行事件（现在没写）；“该加载”由触发用例标出 |
| 误加载率 | 不该加载的对话里，加载了多少 | 同上 |
| 加载后的增益 | 同一批题，有这个 Skill 和关掉它，违规率和期望分差多少 | 单个 Skill 的开关 + 成对比较 |
| 字数与最近评测日期 | 防止越改越长、长期没人看 | 自动统计 |

每个 Skill 配至少 3 条触发用例：应触发、不应触发、边界。连续两轮评测没有加载或没有正增益的 Skill，进入合并或下线评审。阈值是自己定的，公开资料里没有可以照抄的数字。

### 3.5 放置实验

同一批题比三种放法，回答“分层之后规则遵循有没有变差、常驻的提示词少了多少”：

| 组 | 做法 |
| --- | --- |
| 全放系统提示 | 6 个 Skill 的正文全部拼进系统提示，不提供加载工具 |
| 现状 | 模型自己决定加载（改动前的版本） |
| 分层后 | 信号型由服务端附带，判断型补触发条件，5 段迁到工具说明 |

看五个数：拦截级违规率、商业期望分、系统提示字数、每轮输入 token、触发召回。

### 3.6 参考了什么

- [Anthropic 的 Skill 作者指南](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)：先有失败再写 Skill，先建评测再写文档。
- [Anthropic 的企业治理指南](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise)：边加边量召回，掉了就停；每次请求最多 20 个；作者不自审。
- [SkillsBench](https://arxiv.org/html/2602.12670v4)：每个任务配 2–3 个 Skill 收益最大，4 个以上收益减半；面面俱到的长文档几乎没用。
- [野外环境下的 Skill 研究](https://arxiv.org/html/2604.04323v1)：从强制加载到模型自己决定，再到混入干扰项，通过率 55.4% → 51.2% → 43.5%。所以能用信号确定的就不交给模型判断。
- [Intercom Fin 的 Guidance](https://fin.ai/help/en/articles/13975768-provide-fin-ai-agent-with-specific-guidance)：公开资料里唯一做逐条度量的产品（每条被应用的次数和解决率）。体检表照这个思路。

## 4. 自进化

> **目的**：根据商业期望分和规则违规记录，让模型反思哪里没做好，提出对 Skill 的修改。在没看过的题上验证有明确提升，再经开发者审核同意，才生效。模型只能提议，不能自己改完就上线。负责反思和提修改的模型是 Codex，被改进的 Agent 用的是 DeepSeek flash，两者分开。

### 4.1 它不是“记住某个用户的偏好”

|  | 用户记忆（已有） | 自进化（这次要做） |
| --- | --- | --- |
| 改的是什么 | 某一个用户的偏好，例如节奏、交通方式 | 所有用户共用的 Skill |
| 依据什么 | 这个用户说过的话 | 评测题的分数和规则违规记录 |
| 谁点头 | 用户本人，在确认卡上点 | 开发者 |
| 什么时候发生 | 对话过程中 | 线下，跑完一批评测之后 |

### 4.2 一轮怎么走（带防护的版本）

1. **攒记录**：在反思题上跑一遍，每道题记下商业期望分的各个分量、违反了哪条规则。
2. **找问题**：把有违规或分数低的题按“违反的规则”和“拉低分数的分量”归类，看哪一类最多。归类用代码做，不让模型读对话猜原因。
3. **反思并提出修改**：把这一类题给模型看，让它提一条修改。默认是改已有 Skill 的一句；每次都必须成立的要求，提议写成代码规则；现有 Skill 都接不住时才提议新建，并附 3 条触发用例。
4. **验证**：把修改放进候选目录，在验证题上重跑。四道闸都过才算通过（§4.4）。
5. **人工审核**：自动生成一页改动说明：改了哪一句、针对哪类题、前后分数和违规数、各分量的变化、有没有别的题变差。开发者同意才合并。每次修改是一次提交，可以回滚。

举个例子：12 道雨天题里有 5 道没有改排室内。这类失败反复出现，现有 Skill 里没有管天气的，于是提议新建“天气应对”，里面写一句“降水概率高的日子，先查室内候选再排”。在验证题上重跑后违规从 5 道降到 1 道，其他题没变差。改动说明交给开发者看，同意后合并。

### 4.3 ★ 两版对照实验

先做最省事的第一版，再把防护一项一项加上去，两版在同样的起点、同样的预算下各跑三轮，最后在留出题上比。第一版本身就是对照组：防护每一项值多少，由它和第二版的差来说明。

| | 第一版：相信模型 | 第二版：带防护 |
| --- | --- | --- |
| 看什么信号 | 模型自己读对话，自己说哪里不好 | 代码判的违规记录、分数的各个分量 |
| 能改多少 | 可以整篇重写 Skill，可以随意新建 | 一次只改一句；新建要有失败记录和触发用例 |
| 用什么分 | 下单概率 × 综合收益（没有信任折扣和合作酒店上限） | 完整公式 |
| 在哪批题上决定留不留 | 就在反思用的那批题上重跑，总分涨了就留 | 另一批验证题；四道闸 |
| 谁点头 | 没有人 | 开发者 |

第一版预计会出现的四种情况，以及用什么数字看出来：

| 预计的情况 | 为什么会这样 | 看哪个数 |
| --- | --- | --- |
| 反思题上涨得多，留出题上不涨 | 在同一批题上既找问题又验收，挑出来的“提升”里有运气。从 20 个没用的修改里挑最高的，光靠随机波动就能“涨”约 5 个点 | 反思题的涨幅 − 留出题的涨幅 |
| 分数是刷出来的 | 没有信任折扣时，多推佣金高的合作酒店就能涨分 | 把涨幅拆成下单概率和综合收益两部分；首屏合作酒店占比；越位对数 |
| Skill 越改越乱 | 整篇重写会丢掉原有内容；随意新建的 Skill 没人触发或者互相抢 | Skill 总字数、触发召回、没被针对的题的违规率 |
| 模型自己说改好了，实际没有 | 模型评价自己的修改偏乐观 | 模型自评“有改进”的比例 − 实测有改进的比例 |

两版跑完后，一张表并排放：反思题涨幅、留出题涨幅、两者之差、各分量变化、拦截级违规率、Skill 总字数、通过审核的修改数。实际出现了哪几种情况，以实验记录为准。

### 4.4 四道闸，以及其他防护

| 闸 | 条件 |
| --- | --- |
| 目标闸 | 这条修改针对的那类题，在验证题上的违规数明显下降（至少减半，且不是只少 1 道） |
| 回归闸 | 验证题里其余的题，拦截级违规率和商业期望分没有超出随机波动的下降 |
| 分量闸 | 涨分不能只来自综合收益。下单概率和软性匹配分下降的，不通过 |
| 共存闸 | 新建或改了触发条件的 Skill，已有 Skill 的触发召回不能下降 |

其他防护：

- **参数不参与优化**。期望分的权重和阈值是冻结的，自进化只改 Skill。不存在“把权重调到分数最高”。
- **违规是主信号**。违规由代码判，同一份行程每次结果相同。商业期望分是第二信号。
- **保留候选池，不只留当前最高分**。每一类问题各留最好的一条候选，分别验证。只追总分最高的那一条，容易在一类问题上越改越细而其他类没人管。
- **留出题只在实验结束时看**。每轮决定留不留，用的是验证题。留出题整个实验只跑三次：起点、第一版终点、第二版终点。
- **候选目录**。候选修改放在单独的目录里跑评测，不动仓库里的 Skill 文件；审核通过才合并。

### 4.5 参考了什么

- [GEPA](https://arxiv.org/abs/2507.19457)（ICLR 2026 口头报告）：用分数加文字反馈来改提示词，一次只改一处，保留一组各有所长的候选，在没见过的题上验证。
- [ACE](https://arxiv.org/abs/2510.04618)（ICLR 2026）：整篇重写会越改越短、效果变差，所以只做逐条增删。
- [SkillsBench](https://arxiv.org/html/2602.12670v4)：人整理的 Skill 让通过率涨 18 到 25 个点，模型自己凭空写的反而比不用 Skill 还低 8 到 11 个点。
- [Anthropic 的 skill-creator](https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills)：留一部分题不看，专门用来验证修改。
- [AgenTracer](https://iclr.cc/virtual/2026/poster/10007726)（ICLR 2026）：让模型读对话找错因，准确率只有两到四成。所以按违规和分量来归类。
- [一篇 2026 年 10 月的预印本](https://arxiv.org/abs/2610.19084)：提示词自动优化后，验证题平均涨 7.9 个点，没见过的题只涨 5.2 个点。
- Sierra、Decagon、Intercom 公开的做法：版本化、评测关卡、人工审核、先放小流量、可回滚。没有线上流量，用留出题代替“先放小流量”。
- Hermes、OpenClaw：让 Agent 直接改自己的 Skill，没有验证和审核。第一版就是这种做法。
- 完整依据见[调研笔记 04](../../archive/phase1/research/judge-scoring-notes/04_self_evolution.md)。

## 5. 评测集

> **目的**：给前四条线提供证据。两层题库：不花钱的规则题约 600 道；要花钱跑整段对话的多轮题 201 道。题目和标注都由 AI 生成。

### 5.1 两层

| 层 | 测什么 | 多少道 | 每道花多少 |
| --- | --- | --- | --- |
| 规则题 | 每条规则该拦的拦没拦住、不该拦的有没有误拦；打分器算得对不对（§2.6 的检查集也在这一层） | 约 600 | 不调模型，不花钱 |
| 多轮题 | 脚本化用户的整段对话，出行程、出推荐，过规则、算商业期望分 | 201 | 只有被测 Agent 调 DeepSeek flash 要花钱。旧题库实测平均约 0.26 元人民币、29 秒；会出行程草稿的题约 0.6 元、55 秒。这是按全价记账的上限，没有扣缓存折扣 |

### 5.2 ★ 201 道分三份

| 份 | 多少道 | 谁能看 | 用来做什么 |
| --- | --- | --- | --- |
| 反思题 | 61 | 自进化可以读失败记录 | 找问题、提修改 |
| 验证题 | 60 | 只看分数和违规数，不给模型看内容 | 每轮决定一条修改留不留 |
| 留出题 | 80 | 开发过程中不看 | 只用于最终报告；用过多次就换一批新的 |

三份按题目类别分层抽取，划分和题目内容用哈希冻结，改动要另建版本。

### 5.3 201 道怎么当更多道用

- 同一批题比两个版本：新旧版本跑同样的题，只看结果不一样的那些。按现有的随机波动算，201 道这样比，相当于两组各约 400 道互不相同的题。
- 每题跑 3 遍取平均：把单次运行的偶然性压下去。
- 看连续的分数，不只看过没过：现在通过率 84%，只看过没过的话只有一成多的题能分出高下；商业期望分每道题都有信息。
- 提升要超过随机波动才算：门槛约 3 到 4 个点，新基线跑完后按实测波动重算。
- 201 的来历：两个版本在同一批题上比较，80% 的把握检出 6.5 个点的差异，代入 McNemar 检验的样本量公式得到。

### 5.4 题目和数据从哪来

- **类别**：沿用现有 7 类（主流程、信息不全、中途改需求、故障、范围外、记忆、对抗），新增 4 类（商业推荐、雨天、只改一处、预约制项目）。
- **要多出草稿**：现在 30 题里只有 3 题真的产出行程草稿，规则和打分没有东西可评。新题里会出草稿的要占一半以上。
- **离线世界要扩**：现在评测用的合成数据只有 3 个城市、每次 3 家酒店、每城 12 个景点。扩成 6 个城市，每城 12 到 20 家酒店（价格、评分、评价数、坐标、早餐取自一次性录下的乐天快照，佣金和是否合作是模拟设定），景点带室内或室外属性，另有合成天气。
- **题目怎么生成**：每个类别先写几道种子题，再按模板替换城市、日期、人数、预算、出行类型得到变体。同一道种子题的变体不跨三份题。

### 5.5 参考了什么

- [Miller 2024](https://arxiv.org/abs/2411.00640)（Anthropic）：成对比较、每题多次运行都从这里来。同一题跑多次不等于多出几个样本。
- [McNemar 检验的样本量公式](https://support.sas.com/documentation/cdl/en/statug/66103/HTML/default/statug_power_details55.htm)：201 就是用它算的。
- [tau-bench](https://arxiv.org/abs/2406.12045)：除了通过率，再报“连跑 k 次都通过”的比例。
- [Ladder](https://ar5iv.labs.arxiv.org/html/1502.04585)（ICML 2015）：留出题反复用会失效，对策是提升超过门槛才算。
- 可比数据集：tau-bench 115 加 50，[MCP-Bench](https://iclr.cc/virtual/2026/poster/10008216) 104，ChinaTravel 人工核验 154。
- 完整依据见[调研笔记 05](../../archive/phase1/research/judge-scoring-notes/05_eval_size_skill_routing.md)、[07](../../archive/phase1/research/judge-scoring-notes/07_small_eval_power.md)。

## 6. 已定和待确认

- 题目和标注由 AI 生成。
- 自进化的修改必须人工审核后才生效。
- 多轮题做到 201 道。

已定（2026-11-28）：

- Skill 线按第 3 节的“分层”恢复。
- 自进化按 §4.3 先真做一遍第一版当对照组。
- 参数按 §2.6 的方法定，推合作酒店的三个阈值由前沿拐点给出。
- 软性条目不用付费的 Jev 接口，改用本机运行的开源同类模型（选定 Kev-9B，§2.3）。

- DeepSeek flash 的花费上限。
