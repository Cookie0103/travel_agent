# M0 可执行任务规格

按 AGENTS.md §2 批次模式执行。关卡任务：M0.2、M0.3。

**建议批次**：
- 第 1 批：M0.1 → M0.2（M0.2 是关卡，做完后本批结束）
- 第 2 批：M0.3（关卡）
- 第 3 批：M0.4 → M0.5 → M0.6
- M0.7：角色内容由用户先定，再开批

M0.1 最快能在第 1 批之前单独跑，用来测 Codex 一个任务实际需要多久，据此调整后续批次大小。

---

## M0.1 项目骨架 + 上游代码

- **目标**：能用 `scripts/dev.py` 的 `setup`、`check`、`test` 三个命令跑通的空项目，且在 Windows 原生 PowerShell 下可用。
- **产出**：
  - `pyproject.toml`、`uv.lock`、`scripts/dev.py`（命令见 AGENTS.md §4）、`.gitattributes`（`* text=auto eol=lf`）、`.env.example`、`.pre-commit-config.yaml`、`docker-compose.yml`（只含 PostgreSQL）
  - 目录骨架（按 02 §10），每个包有 `__init__.py` 和 `README.md`
  - import-linter 配置（AGENTS.md §3.1 的三条分层规则）
  - `scripts/fetch_upstream.py`：把两个上游仓库 clone 到 `vendor/` 并 checkout 到 06 §2 的固定 commit；已存在则跳过。commerce-agents 拉取失败则报错退出；**DataMind 拉取失败（无权限或无网络）只打印警告并继续**，M0.6 之前不需要它
  - 一个 smoke 测试
- **验收**：
  ```bash
  uv run python scripts/fetch_upstream.py
  git -C vendor/commerce-agents rev-parse HEAD      # = fd4d592...
  uv run python scripts/dev.py setup
  uv run python scripts/dev.py check                # 退出码 0
  uv run python scripts/dev.py test                 # 退出码 0
  git status --porcelain vendor/ .env               # 无输出（已忽略）
  ```
- **理解问题方向**：分层规则在防什么；为什么 vendor 不能提交。

## M0.2 DeepSeek 协议实测

- **目标**：用真实 DeepSeek 逐项验证 02 §4.2 的差异表。
- **产出**：`tests/live/test_deepseek_protocol.py`（标记 `live`）；`docs/protocol-deepseek.md` 记录每项的请求、实际响应、结论。
- **必测项**：06 §5 待实测清单中 DeepSeek 的 5 项；外加 `is_error` 是否被忽略、`cache_control` 是否报错。
- **验收**：`pytest -m live tests/live/test_deepseek_protocol.py -v` 输出逐项结果；文档中每项标「符合文档 / 与文档不符 / 无法判断」。
- **费用**：DeepSeek 按人民币线路检查 `DAILY_BUDGET_CNY`；不消耗 Anthropic/OpenAI 的 `DAILY_BUDGET_USD`。真实调用前先实现并离线验证预算拦截；还需同时遵守用户当前批次的调用次数上限。

## M0.3 中立消息格式 + AnthropicProvider

- **目标**：02 §4.1 的 `Message` / `ModelProvider` 契约及 Anthropic 格式实现。
- **产出**：`backend/providers/` 下的消息模型、`AnthropicProvider`（流式，事件为 text_delta / tool_call_ready / usage / completed / error）、中立格式 ↔ Anthropic 格式的转换。
- **验收**：
  - 单测：转换往返无损；`provider_meta` 在切换 provider 时可丢弃；未配对的 tool_call 被拒绝（R02）。
  - live：同一段两轮工具对话在 DeepSeek 上续接成功；Claude 小样本可选。
- **依赖**：M0.2 的结论（如思考模式处理方式）。

## M0.4 CLI 薄片

- **目标**：命令行里问「京都有哪些室内景点」，Agent 调工具并回答。
- **产出**：最小 fixtures（约 20 个景点、12 段攻略，03 §7）；`search_places`、`search_content` 两个只读工具；有界 Agent 循环（02 §3：轮次上限、最后一轮强制不调工具、中断补齐配对）；`python -m backend.cli` 入口；FakeClient。
- **验收**：
  - `dev test`：FakeClient 脚本化测试覆盖正常往返、轮次上限收尾、未知工具（R01）。
  - live：`python -m backend.cli "京都で雨の日に行ける屋内スポットは？"` 能看到工具调用与最终回答。

## M0.5 OpenTelemetry + Langfuse

- **目标**：一次 CLI 运行在 Langfuse 里看到完整 trace（02 §8.1 的 span 结构）。
- **产出**：`docker-compose.langfuse.yml`（或按 ADR-000 改用 Cloud）；tracing 初始化模块；模型调用、工具调用各一个 span。
- **验收**：运行 M0.4 的 CLI 后，Langfuse 中能看到 1 个 trace，含模型 span（带 token、实际模型名）和工具 span（带参数摘要、状态）。贴截图或 trace 链接。
- **注意**：span 中不得出现密钥和完整 prompt（AGENTS.md §5）。

## M0.6 评测骨架：导入 DataMind 21 条

- **目标**：`dev eval-dev` 能跑出结果表。
- **产出**：
  - `eval/cases/datamind_adapted.jsonl`：按 05 §1.1 改编（工具名映射、三类处理），每条保留原 `id` 并注明来源；
  - `eval/run.py`：读取用例 → 跑 Agent → 规则评分 → 输出表格和 JSON 结果；
  - 规则评分器：工具选择、无多余工具、是否有结果、超范围处理（参考 `vendor/datamind-ai-agent/agent-loop/claude-managed/eval/src/graders/code/` 的思路，用 Python 重写）。
- **验收**：`dev eval-dev` 输出 21 行结果 + 通过率；`dev eval-dev --live` 用 DeepSeek 跑一次，结果存为 baseline。

## M0.7 角色规格 + 语气评测

- **目标**：05 §3.1 的语气评测能运行并完成一次人工校准。
- **产出**：`backend/agent/persona.md`（角色规格，必须做 / 禁止做 / 长度）；对应的规则评分器；LLM 评审（0–5 分，每档有标准和示例）；`eval/calibration/` 存人工打分。
- **验收**：对 20 条回答，LLM 评审与人工打分「相差 ≤1 分」的比例写进 `docs/journal.md`；比例过低时记录改了评分标准的哪里。
- **停止点**：角色规格内容由用户决定，Codex 只给草案。
