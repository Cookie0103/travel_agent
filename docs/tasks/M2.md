# M2 模拟预订与恢复：可执行规格

依据plan/02 §6、03 §6、04 M2、05 R09–R12/R16。复用现有SDK、工具执行器、身份、Evidence与真实PostgreSQL；不造第二套runtime、队列或多worker租约。

## M2.1 独立模拟供应商

- 独立FastAPI进程提供POST /holds、POST /orders、GET /orders?client_ref；模拟数据与Travel业务表分离，使用项目PostgreSQL，服务重启后幂等仍成立。
- hold_id/订单ID服务端生成；输入是完整不可变报价口径，不允许未知总价假装确定。hold默认15分钟、过期释放；同client_ref重复同内容返回同一订单，不同内容拒绝。
- 请求头显式注入延迟、429/Retry-After、500、创建订单后丢响应；默认无故障，只限本地模拟，不接真实供应商。只在测试/显式演示配置启用。
- 验收：真实PG竞争/重启、过期、非法与不一致参数、四种故障；实际HTTP启动与读写。复用已有数据库配置/事务/迁移，不加数据库框架。

## M2.2 Booking与用户确认（自动关卡）

- 状态quoted→held→confirmed→booked，失败/unknown/expired与每次转移历史持久化；client_ref来自稳定booking_id。
- hold_hotel工具只接受本人/本会话已查询且当前revision/未过期的offer；锁定报价与hold期限返回卡片，模型无下单/确认工具。
- POST /bookings/{id}/confirm独立用户API，GET状态与会话列表供恢复；检查归属、条件、hold有效期后持久化确认，再调用供应商。
- 网络调用不伪装成DB原子事务；请求未知先对账，不能通过页面重复确认直接盲重发。报价未知税费拒绝hold并要求完整报价。
- UI明确模拟、确认对象/金额/期限、状态；确认响应丢失后读取状态，保留原booking_id。
- 验收：两用户隔离、伪造/过期/旧条件、不完整报价、重复/并发确认、模型声称确认不能下单、过期释放与数据库回滚。

## M2.3 有界重试与对账

- 只有预订服务处理重试；429按合法Retry-After等待，次数和总时间有界；非法/过长值不能导致无限等待。500与连接/读超时按可证明的确定失败/不明状态分类。
- 下单结果不明标unknown，按client_ref查询；查到booked、可证明不再产生订单才failed、查询失败或暂时未找到保持unknown。一次查无不能排除迟到创建；模拟供应商在锁内检查hold过期和订单，提供明确终态缺席证据。供应商幂等不能替代应用先对账。
- confirmed在调用前崩溃与调用后未落库均先对账；无明确订单/未发送证据时不自动再下单。普通页面读状态不触发模型。
- 验收R09–R11：订单已创建而响应丢失→unknown→booked且一单；查询失败/限流/500/超时、重复确认和重启不重复创建；超时先查无、稍后迟到创建不能误判failed。

## M2.4 业务断点与SDK恢复（自动关卡）

- 检查现有SDK会话持久引用/文件与运行记录；中断后先核对DB条件、已提交草稿/hold/booking与工具业务幂等，再决定安全续接或partial/awaiting_user降级。
- 业务写入使用稳定幂等键，覆盖新SDK tool_call_id再次到达；不编辑SDK transcript，不假设SDK保存与DB同事务。
- 显式恢复若产生模型请求仍受原额度；启动/SSE/GET不能偷偷调用付费模型。单API进程恢复，不引入C档worker调度。
- 真实进程故障覆盖DB已提交/SDK未保存、反向窗口、SDK会话丢失/损坏、条件已变、取消与迟到结果；已提交写入不重复，unknown预订先对账。

## M2.5 SSE补发与快照

- 复用现有游标/持久事件，终态与快照一致；UI断线只读重连，去重展示，网络丢消息POST/确认响应后通过稳定ID读取/显式重试。
- 实际HTTP/浏览器断线与进程重启验证，不能仅靠函数替身；模型/工具调用次数不因SSE重连增加。

## M2.6 故障回归与归因

- R09–R12/R16整体回归，至少一个真实开发失败提供Trace→根因→修复→回归证据；注入实验标为实验，不称线上事故。
- dev check/test、前端契约/type/lint/test/build、独立审查后本地提交；证据合入M2集中记录与执行计划，继续M3。
