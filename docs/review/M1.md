## M1.1 API 与数据库

- 阅读顺序：api/app.py create_app → services/sessions.py SessionService → persistence/sessions.py → models.py。
- 调用链：HTTP验证输入 → 服务解析令牌身份 → 每次操作独立数据库事务 → 仓储SQL → 返回不含内部异常的响应。
- 不变量：客户端不指定user_id登录；令牌只保存SHA256摘要；查询同时约束session_id/user_id；tests/integration/test_sessions.py保护隔离、过期、事务落盘和数据库失败。
- 测试库：每次创建随机专用库，迁移两次并检查漂移；清理只允许当前创建的库，URL query不能改变连接路由。
- 失败处理：无身份401、越权/不存在404、关闭演示入口403、数据库不可用503；错误不含连接密码。
- 取舍：直接使用SQLAlchemy会话与少量业务仓储；不新增通用CRUD框架。演示令牌足够验证用户隔离，生产认证留明确边界。
- Windows实际启动发现loop回调返回类型错误，已改为事件循环实例并加回归；HTTP健康/登录/会话/隔离实测见evidence/m11-api-smoke-2026-10-03.json。
- 数据库迁移成功；最终check87文件/3契约通过，dev test205 passed/2 deselected（17.60秒），独立复核通过。CI仅已配置，未远端运行。
- 这里的重开应用读取会话只证明数据库持久化，不代表M2预订恢复已完成。

## M1.3 条件与事实证据

- 阅读顺序：domain/travel_request.py → services/travel.py patch_request/resolve_evidence → persistence/travel.py → domain/evidence.py。
- 调用链：API或工具注入RunContext → 锁住本人会话 → 检查expected_revision → 合并set/clear并验证 → 同事务更新revision/证据失效。
- 同一个TravelConditions生成输入/schema与当前状态；省略表示保留、clear显式清除，无变化不加版本。酒店要求明确儿童年龄（无儿童用空数组），不能假设补齐。
- Evidence补全核对本人/本会话、当前revision、适用日期人数、有效期；任何伪造ID都失败，不丢弃后继续展示。来源缺失是unknown。
- 真实数据库测试证明竞争只有一方成功、写后异常整笔回滚、旧revision/过期/错误条件拒绝；普通会话与旅行服务复用同一事务函数。
- 独立审查发现当天往返被酒店晚数约束拒绝；已改为旅行允许同日，hotel_requirements单独要求至少一晚，并添加对照。
- 取舍：每会话一把数据库行锁，规则简单可验证；不提前实现C档多worker租约。同用户旧revision证据也拒绝，避免悄悄沿用旧条件。
- 验证：修复后check102文件/3契约、完整238测试通过（18.83秒），项目库升级0003，独立复核通过；不把测试中的故障注入当真实线上事故。
