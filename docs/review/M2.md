# M2 模拟预订与恢复集中记录

## M2.1 供应商

- 调用链：mock_supplier.app → SupplierService → supplier_holds/supplier_orders；独立HTTP进程，复用现有PG连接/事务/迁移，表与Travel用户/Evidence独立。
- POST holds只接受有效完整报价，并用既有quote对照目录；不复制金额计算。每个client_ref产生一个hold，订单在hold行锁内生成一次，重启后仍返回第一笔。
- 四故障仅显式启用：delay、429/Retry-After、500、订单已提交后HTTP传输中断。正常启动故障禁用。
- 一次查无可能是订单仍在执行，不能标失败；只有锁内检查hold已过期、又没有订单，才返回absence_final。
- 真实HTTP实验观察ReadTimeout→暂查无且absence_final=false→迟到下单完成，同键请求仍一单；丢传输后RemoteProtocolError，对账读到booked。两者均是故障注入实验，无外部真实预订。
- 专项4通过/check152文件通过；完整/审查/提交结果见执行计划。应用Booking/页面确认和重启恢复仍需后续实现，不把供应商接口当整个M2完成。

理解问题：为什么供应商幂等不等于可以盲重试？为什么超时后查不到订单也不能判failed？数据库行锁保护的范围为什么不包含外部HTTP事务？

- 独立P2：报价金额正确但可伪造延长到期。修复复用quote原quoted_at重算，除随机offer_id外完整比较，加入旧报价延期失败回归；不另写TTL规则。

## M2.2/2.3 预订与对账

- 调用链：SDK hold_hotel / 页面暂留 → BookingService → HTTP SupplierClient → 模拟供应商；用户独立confirm API提交confirmed后才发送order。共享服务/报价契约，不复制runtime。
- 持久保存报价、来源、版本、状态历史与稳定client_ref；同报价重复暂留返回原ID。held按15分钟锁价，与原quote的5分钟有效期分别裁决；旧旅行条件不能确认。
- 429最多3次、总5秒；500/超时/损坏写响应按unknown处理，重复confirm只对账。暂查无不能判failed，只有供应商锁内过期缺席证明可以。实际HTTP响应流中断后重建服务查到原订单，无重复订单。
- API两用户隔离、非法参数、重复确认及真实PG竞争通过；实际SDK本地模型脚本完成search→hold，供应商订单仍为零。真实浏览器完成比较→暂留→用户确认→booked，刷新保留同一订单，截图见[页面证据](../evidence/m22-booking-workbench.jpg)。无真实外部订单/模型费用。
- 独立审查P2修复：合法长偏好条件造成工具结果超限，改用Booking.card复用offer.card；随机UUID前50条截断隐藏活动预订，改为全部本人预订按创建时间稳定读取。新增三组20×200字条件与51历史记录回归，不添加通用分页框架。大规模历史分页是后续性能优化，当前不静默省略任何预订。
- 最新完整/专项/前端检查见执行计划；实际杀进程与DB/SDK非原子保存窗口仍是M2.4待办，不能用服务对象重建冒充完整进程恢复。

理解问题：模型为什么不能替用户确认？unknown为什么先查询而不是重试？报价到期与hold到期有什么区别？工具卡片为什么不直接返回完整数据库对象？

## M2.4 断点与恢复

- 业务结果是PG事实；patch/stage稳定参数键与写入同事务，不能靠SDK tool_call_id判断是否执行过。相同语义默认值、clear顺序/金额格式规范化；保留“未修改/显式清除”的业务区别。重放仍核对revision/base/期限/Evidence，不给旧事实延长有效期。
- SDK正常完整轮次由私有checkpoint关联，复用[官方SDK会话接口](https://code.claude.com/docs/en/agent-sdk/sessions)；指纹只读核对，模型无文件工具。API进程重启后可恢复正常会话；未完成轮次不透明重放，从当前条件/有效draft与booking快照新建。状态、SDK文件和工具业务不是同一事务。
- 启动将旧running标partial、旧cancelling标cancelled，状态和终态事件同事务；读取/启动不生成模型费用。PG启动不可用仍提供503，待数据库恢复后先核对，再受理新执行。
- 实际PG子进程commit后kill覆盖条件/草稿与预订供应商提交前/后；0/1订单保持稳定，confirmed重启只对账。实际API kill→重启→partial/SSE游标补发/原消息去重/新消息完成。实际CLI正常分进程resume与文件丢失/半JSON损坏/条件/CLI变化均验证，轮中另连接修改条件不保存指针。
- 独立3P2已修复复核关闭：默认参数键不等价、缓存跳过Evidence、旧SDK上下文误标新revision；新增失败回归。完整回归随后发现PG不可用使启动退出，保留原503测试并修复延后恢复，专项15项通过；最终结果见执行计划。
- 已支持单API恢复，未实现C档多worker/租约；未完成SDK轮次安全降级，不宣称任意指令位置透明恢复或SDK与DB原子提交。

理解问题：SDK resume为何不能证明业务执行一次？为什么参数默认值会影响恢复？为什么重放已提交草稿还要检查Evidence？为什么条件在模型执行中变化后应新建SDK会话？

## M2.5/2.6 断线与失败证据

- 实际浏览器API断线→POST失败→刷新保留原身份/待重试消息→恢复后显式重试原ID，仅新增一次执行；只读SSE重连后运行数、run ID与事件序号不变。运行中API kill与游标补发另由真实HTTP子进程测试覆盖，不宣称浏览器中途断流。
- 独立审查发现明确401时没有重新认证入口，修为仅401清无效身份并显示显式创建按钮；网络/5xx保留身份。实际浏览器临时过期自建demo→401→重新创建成功，随后复原原期限，旧订单/行程未改。截图见[断线](../evidence/m25-network-outage.jpg)、[恢复](../evidence/m25-network-recovered.jpg)、[401](../evidence/m25-expired-identity.jpg)。
- API从已提交事件复用OTel exporter写私有.cache/api-traces；span只含工具名/服务端schema字段名、实际revision/Evidence ID和时间，全文不导出。未知参数名也可能携带全文，独立P2已通过schema白名单修复并加入validation回归。写盘失败只记安全警告，业务completed仍可读；未观察到的usage不编造为零或成功采集。
- 复核已有真实hakone-onsen失败：Trace显示完成执行却调用4次无必要工具；结合京都覆盖范围和旧提示词确定需求理解缺口。M0.7已补明确范围规则，同一用例一次真实回归无工具通过；本轮重读并整理[脱敏证据](../evidence/m26-failure-regression-2026-10-03.json)，不新增费用、不宣称总体效果改善。M3仍需补其余真实坏例和5类注入对照。
- 387完整测试/前端7测试+构建/check170通过后独立发现两P2，修复后19专项及静态/前端复核通过；最终提交钩子再验全表。不同代码版本的结果分开记录，见执行计划。
- 401修复进一步复核出旧流/普通API迟到写回及Promise微任务间隙；generation和每次同步写回前的active检查保护新身份，3新增异步回归及前端10/type/lint/build通过。浏览器401流程与这些单位回归分别标注，不声称浏览器穷举并发顺序。
