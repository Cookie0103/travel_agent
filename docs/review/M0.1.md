# M0.1：现在到底做到了哪里

**一句话：开发环境和目录已经搭起，工程检查与 37 个离线测试已通过；旅行 Agent 本身仍未实现。**

## 已经做了什么

- 建好前端、后端等目录，写明以后各自放什么；多数目录目前只有说明文件和空的 Python 包。
- 准备 Python 3.12、开发工具和依赖版本记录，便于以后在同样的环境下运行。
- 写了两个辅助程序：dev.py 帮你安装、检查、运行测试；fetch_upstream.py 下载指定版本的参考代码。
- 写了检查这些辅助程序的测试，并记录实际操作、失败原因和恢复步骤。
- 阅读参考项目，整理工具调用的流程；读懂别人的实现不等于我们已经做出来。

## 现在没有什么

没有可用的网页、HTTP API、DeepSeek/Claude 调用、Agent 思考与调用工具的循环，也没有景点查询或数据库业务代码。
所以“37 个测试通过”不表示旅行助手已经可用，只表示本次工程辅助功能的测试通过。

## 阅读顺序与主调用链

1. 先看 [项目首页的目录表](../../README.md)，知道代码应该放在哪里。
2. 再看 scripts/dev.py 的 main：例如你输入 test，它启动 pytest，pytest 才去执行 tests 里的测试。
3. 再看 scripts/fetch_upstream.py 的 main → fetch → git：下载参考仓库，检查是不是指定版本。
4. 需要技术错误细节时，再看 [未完成原因](../blocked/2026-10-02-m0-core.md)；不必先读所有日志。

本批只写文件和开发环境，没有运行旅行业务，也没有用户行程状态可保存。
真正的 Agent 以后放在 backend/agent，模型连接放 backend/providers，HTTP 路由只是 backend/api。

## 必须保持的规则（不变量）

- 默认测试不能花钱调用模型：tests/test_dev.py 和 test_offline_default.py 保护这点。
- 各层不能随意绕过职责直接调用：tests/test_architecture.py 检查，例如 API 不能直接访问数据库层。
- 参考代码版本不对不能擅自覆盖：tests/test_fetch_upstream.py 检查已有目录被保留。

## 之前为什么失败，现在如何处理

- 之前测试替代对象的写法不符合类型检查，共 5 处；现已改正目标引用方式，没有放宽检查。
- 格式化工具之前连设计文档的代码示例也检查；现在限定为 Python 文件和 pyproject，设计原文保持不变。
- 用户终端的 21 个错误来自共享临时目录权限。dev test 现在每次创建自己的项目内临时目录与缓存，不改系统权限、不删旧文件。
- 10 月 2 日曾按两轮失败规则停在 wip；本次用户报告报错后修复并复核，在 batch/2026-10-03-m0-repair 留待审阅。
- Docker 和本机两套 PostgreSQL 均已确认运行；当前工程检查无需数据库，也未启动项目数据库容器。
- scripts 遇到环境错误会退出并给出原因；环境问题集中记录到 docs/blocked/environment.md。

## 取舍

本批先安装检查和测试工具，等后续任务再安装模型等业务依赖。另一个选择是一次装齐，暂不采用，以免提前固定未验证接口。
这些规则帮助人和 AI 及时发现错误，但它们本身不负责旅行规划，也不是 Agent 的执行循环。
