## 简历条目（中文）

**旅行规划 Agent（个人项目）｜2026.10**

面向日本旅行 OTA 场景的对话式规划 Agent：用户在聊天窗口描述需求，系统比较乐天酒店、查询 Google 景点与路线和天气，生成可校验的行程草稿，用户确认后保存；确认过的偏好跨会话保留。模型负责理解需求和编排工具，后端负责事实校验、约束检查和失败恢复。项目开发中使用 AI 编码助手，我负责架构取舍、测评设计、问题定位与验收。

**技术栈：** Python / FastAPI / PostgreSQL / Next.js；Claude Agent SDK（DeepSeek 兼容线路）/ 自定义旅行工具 / MCP；OpenTelemetry + Langfuse；Railway / GitHub Actions

1. **确定性代码兜底的 Agent 架构：** 模型自主选择 19 个自定义工具（线上开放 18 个），但身份、版本、金额、时间、预算和事务全部由服务端裁决：模型只传 ID，价格与来源由服务端按 ID 填入；模型没有保存行程或下单的工具，必须由用户在页面点击确认。旅行条件每轮从 PostgreSQL 重读（带版本号），不依赖聊天记录。
2. **生成—校验—修复循环：** 行程由纯代码校验（35 个以上检查码：日期、营业时间、路线间隔、重复景点、预算等）；冲突先由服务端做有界、单调的局部修复（最多 12 个操作、冲突数必须严格下降、不新增景点、不放宽校验），修不掉再反馈给模型，且有轮数上限。
3. **服务端发卡的交互流程：** 城市、日期、人数齐全后由服务端发一张合并确认卡（起床、到达、住宿、禁烟、床型等），不依赖模型自己决定怎么追问；酒店不自动替用户选，所有住宿段选齐才规划。起因是真实运行中模型曾用文字追问并声称"请在卡片里确认"。
4. **长期记忆与隐私边界：** 模型只能提议、须引用本轮用户原话，用户在卡片上点选才生效；只有节奏、交通、起床、结束时间 4 项可长期保存，其余只对本次行程有效；删除时清除事实正文并切断旧会话续接。
5. **外部 API 的失败处理：** 接入乐天、Google Places/Routes/Geocode、Open-Meteo。429、超时、5xx 在调用所属的一层重试一次（`Retry-After` 最多等 3 秒，单次超时 8 秒），受总期限和配额约束，失败时只报告真实尝试次数。对模拟供应商的预订实现了幂等键、`unknown` 状态对账，4 个真并发测试各跑 25 轮。
6. **端到端测评体系：** 设计 30 道多轮任务，覆盖主流程、需求澄清、中途变更、工具故障（9 种注入）、越界、对抗、长期记忆 7 类，调用真实 DeepSeek 与乐天、Google API，每题重复 3 次衡量稳定性；成败由代码核查数据库终态与工具轨迹判定，长期记忆按"提取—落库—跨会话注入 prompt—行为生效"四层校验，并对账回复中的虚假声明。**在自建的 30 题评测集上，任务成功率 96.7%（87/90），稳定通过率 93.3%（28/30）。** 测评自身的缺陷（脚本、运行器、判定过松）也被逐条定位并修复，据此还暴露出 2 项真实短板：局部修改已有草稿（1/3）和规划完整度（2/3）。
7. **可观测与工程化：** OpenTelemetry 记录每次运行、工具调用和模型请求，每次测评运行向 Langfuse 推送 20 多项数值分数（不上传回复正文）；测评支持故障注入、中断续跑和额度保护；约 2460 条离线测试、11 条导入层契约、3 个 CI job，约 29 篇 ADR 记录取舍。

## 精简版（项目经历只给 3 行时用）

- 设计并实现日本旅行规划 Agent：模型自主调用 19 个工具（乐天酒店、Google 景点/路线、天气），服务端负责事实校验、有界修复、版本化状态和用户确认；FastAPI + PostgreSQL + Next.js，部署在 Railway。
- 建立端到端测评：30 道多轮任务 × 3 次真实运行，代码核查数据库终态与工具轨迹，覆盖故障注入、越界、对抗与四层长期记忆校验；**自建评测集上任务成功率 96.7%，稳定通过率 93.3%**，并定位出局部改程与规划完整度两项短板。
- 实现外部 API 重试与配额、预订幂等与对账、OpenTelemetry/Langfuse 可观测；约 2460 条测试与 3 个 CI job。

## 30 秒介绍

用户想去日本玩，要比较酒店、查路线、反复改行程。我做了一个让模型调用工具出方案、由代码守住事实和约束的 Agent：模型只传 ID，价格和来源由服务端填；行程要过纯代码校验，冲突先由服务端做有界修复；保存和预订必须用户在页面点确认。我还自己设计了 30 道多轮测评题，用真实 API 每题跑 3 次，成败由代码查数据库判，不靠模型自评。这套测评既量化了稳定性，也帮我发现了两个真实短板，同时暴露过我自己测评脚本里的几个 bug。

## 必须带上的限定

写进简历或回答追问时，下面几条不能丢：

1. **"在自建的 30 题评测集上"**。这是本系统（模型加服务端校验与状态机）的完成度，不是模型的通用能力；没有对照组，不要和别的 Agent 比。
2. **数字是修复后的结果**。首轮原始成绩是 84.4%（76/90）、稳定通过率 80%（24/30）；最终是修好测评脚本与运行器、加严 3 道规划题判定后，对部分题目重跑并拼接。拼接说明在 results 文档。
3. **没有留出集**。题目在测评过程中被修改过，用一批全新的题测，成绩可能更低。
4. **预订是模拟的**。线上真实酒店只提供乐天链接，不暂留、不下单；幂等和对账针对模拟供应商。
5. **只验证了 DeepSeek 线路**。Claude 原生线路没有真实验证，不要写模型对比。
6. **judge 的体验分未经人工校准**，不要引用。
7. **AI 协作**要如实说。分支提交里有 Claude、Codex、Cursor 的联合署名；我负责架构取舍、测评设计、问题定位与验收，会被追问"哪些是你写的"，请准备好具体回答。

## 被追问时的底气

- **每题有完整对话和 trace 可查**，成败由代码判定，不是模型说"完成了"就算。
- **失败如实保留**：首轮 84.4% 没有被藏，改判的唯一一处人工复核是往更严的方向改（"只替换一处"由 3/3 改为 1/3）。
- **能讲出具体的故障故事**：模型用文字追问还谎称有卡片；测评判定过松把残缺行程算成功；一个测试意外跑了真实调用；测评自设配额掩盖了真实表现（见架构复盘 §6）。
