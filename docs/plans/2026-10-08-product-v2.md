## 3. 评审与设计（Claude，2026-10-08）

### 3.1 计划整体评价

原规划（07）的优点：证据分级严谨（不把“代码能解释”写成“已证实根因”）、阶段可回退、边界矩阵完整、面试材料意识强。需要修正的地方：

2. **关键契约没提前定**：R1 必须新增历史接口，但原计划推到“实施时再确认”，会卡在阶段中间 → D2 前置到 R0。

### 3.3 设计要点

**R1 一次旅行 = 一个 session**
- 后端新增只读：`GET /sessions?limit&cursor` 返回当前用户的旅行摘要（session_id、目的地、日期、当前正式 plan_id/版本、最后更新）；`GET /sessions/{id}/runs?limit&before` 返回轮次（prompt、answer、status、error_code、presentations、draft_id）。都按身份校验归属，有界分页。复用现有 persistence 查询风格，不加新表。
- 前端状态从“一个 run”改为“当前 session 的 runs 列表”；localStorage 只存 token + 当前 session_id；历史从接口读。
- “新建旅行”= 用已有 token `POST /sessions`，不重新 demo login。“我的行程”按 session 列出正式行程。
- 卡片、草稿徽标、SSE 事件都绑定 (session_id, run_id)；不属于当前 session 的迟到事件丢弃。

**R2 “模型说完成”与“业务已提交”分开**
- run 结果附带业务结果：`answer_only | draft_staged(complete/partial/conflict) | stage_failed(code) | confirmed(version)`，由服务端从可信工具结果和原草稿确认版本推导（ADR014：复用既有tool_finished小元数据，无新表；旧成功/最新stage无结果为unknown/null）。前端按它显示状态，回复文字不决定状态。
- `plan_exists` 等失败给出下一步：“修改现有行程”或“新建旅行”。
- RunSteps 显示错误类别中文说明（映射表，不显示内部参数）。
- 正式行程永久可看；“报价/引用过期”只作用在对应条目。

**R3 条件只提交用户真正改过的字段**
- 表单与上次服务端值做 diff，只 PATCH 改动字段；无改动不发请求。`mergePace` 去重；空字段不再回退成京都/50000 等示例值（示例只做 placeholder）。
- 儿童：“无儿童”与“儿童人数 n + 每人年龄（允许 0）”分开。
- 预算：`budget`（全程）+ 可选 `lodging_budget`（D5，全程中的住宿分项）。规则见 §3.5。含糊表达先澄清。
- validator 新增 warning：每天景点数与节奏不符、重复景点（同 place 跨天出现）；住宿/餐食/交通段不计入。
- 状态与错误文案用中文模板；回复语言做固定输入回归。

**R4 酒店 Bug（不含新功能）**
- 按 hotelNo 分组：一张卡 = 一家酒店，房型/套餐在卡内切换；“4 家”指不同酒店数，不够就如实显示数量。

- 解析已请求到的地址、经纬度、评价数（缺失为未知，不造值）。

### 3.5 用户 2026-10-08 追加的两条要求

**(1) 全程预算与住宿预算的关系（D5 细化）**

- `budget` = 全程预算：交通、门票、餐饮、住宿等全部费用的上限。`lodging_budget` = 其中**住宿部分**的预算，是全程预算的一个分项。
- `basis=per_room_night` 时，住宿总额 = 每房每晚 × 房间数 × 晚数；`basis=total` 时即住宿总额。
- 两个预算均按用户原话保存，不暂缓写入、不调整金额；冲突不另存标志，由 validator 从当前值推导（D6）。
- 住宿金额先按 basis 换算成住宿总额区间：下限 > 全程预算为 **conflict**；仅上限超过为 **warning**（例：每房每晚 2–3 万 × 1 房 × 2 晚 = 4–6 万，全程 5 万，只警告）。等于上限不算超过。
- 按 basis 判断所需信息：每房每晚预算的晚数或房间数未知，或者两个预算币种不同，结论为“无法判断”；不估算、不换汇。`basis=total` 已是住宿总额，不需晚数/房间数。
- 冲突时助手先在对话里追问以哪个为准，解决前不做酒店比较；若仍生成草稿，ValidationReport 为 conflict，沿用现有规则不能确认。用户回答后只更新其明确改动的那个字段，revision 正常增加。
- 例：“全程 5 万、每房每晚 3 万、两晚”（已知 1 房）→ 两个值都保存，住宿总额 6 万 > 全程 5 万，判冲突后追问。若房间数未知，则先追问，结论为无法判断。
- 只给了全程预算：住宿预算为“未知”，不自动按比例拆分，不把全程预算当作每晚预算（B06 的错误）。只给了住宿预算：全程预算保持未知。
- 酒店比较、价位判断用住宿预算；整个行程的费用校验用全程预算。“上限”不是“最低消费”，不为花满预算而排除便宜但合适的选项。
- 示例：“全程 6 万，酒店每晚 2–3 万” → `budget=60000`、`lodging_budget={20000–30000, per_room_night}`，两者并存。（ADR-015 必须保留范围的上下限，以支持 D6 的冲突/警告区分；不能仅存上限。）

## 5. 边界与不变量（每个相关任务都要覆盖）

| 边界 | 必须维持 |
| --- | --- |
| 新标签/新建旅行/切历史 | 新标签默认恢复上次旅行；“新建旅行”后是空摘要，不带旧结果 |
| 同一身份第二次旅行 | 复用 token，新 session；不重新登录 |
| 两标签并发、迟到 SSE | 状态绑定 session+run；旧事件不覆盖当前选择；版本冲突给提示 |
| 发送响应丢失/重连/SSE 重复 | client_message_id、sequence 去重；读历史不重跑模型、不重复付费 |
| 数据库/网络失败/重启 | 已提交正式版本保留；读失败显示错误，不显示“没有行程” |
| 草稿过期/条件改变/已有正式版本 | 保存时再校验 revision/base_version；修改旧行程走 patch，新旅行走新 session |
| 确认双击/提交成功读回失败 | 只生成一个版本；读回失败可重读，不再保存第二份 |
| no-op/隐藏默认值 | Decimal 与规范化后比较；无变化不增 revision、不清卡片、不注入示例值 |
| 日期/预算/人数 | 结束早于开始拒绝；当天往返不搜住宿；0 儿童≠0 岁；人数房数不整除时总价未知；不跨币种换汇 |
| 限制房型/无价格/多晚缺报价 | 资格未知不推荐为适合；未知不填 0；缺任一晚报价不声称总价完整 |
| 候选不足/重复/额度不足 | 计数是不同酒店；不为凑数循环查询、不扩大额度 |
| 富文本 | 不执行 HTML；只允许 https 与站内链接 |
| 前后端部署不同步 | 新字段向后兼容；旧前端+新后端、新前端+旧后端都可用 |
